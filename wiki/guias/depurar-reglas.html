Asignatura / Guías / Depurar reglas

Depurar reglas Qué se ha disparado, qué ha ganado, y qué no se dispara nunca.

En una máquina de estados se ve en qué estado está el personaje. En un sistema de reglas no hay nada que mirar: en cada turno se disparan unas cuantas reglas, gana un ACTION y el resto desaparece. Esta guía da dos herramientas para verlo, una para probar reglas sin jugar y otra para seguirlas mientras se juega, con el código entero y lo que sacan de verdad con el ejemplo de las siete reglas.

01

Tres preguntas, en este orden

Cuando Ms. Pac-Man hace algo raro, la causa está en uno de tres sitios, y cada uno se mira con una herramienta distinta. Id en orden: no tiene sentido revisar una acción si su regla no se dispara.

PreguntaSi la respuesta es noCómo se mira
1 · ¿Se dispara la regla? Falta un hecho, o un slot no vale lo que creéis, o un símbolo está mal escrito. Un caso en ProbarReglas, o el resumen de la traza: "0 veces".
2 · ¿Gana su ACTION? Otra regla aserta un ACTION con más priority en el mismo turno. La traza: dice quién gana y quién pierde, con su priority y su info.
3 · ¿La acción hace lo que debe? El problema ya no es de reglas: es Java, como en la Práctica 1. VerPartida despacio, con la traza diciendo qué acción se está ejecutando.

Todo el código de esta página está en el proyecto del ejemplo, en el paquete depurar.

02

Probar las reglas sin jugar

Esperar a que en una partida se dé justo la situación que queréis probar es lento y no se puede repetir. Es mucho más rápido escribir la situación a mano, como hechos, y preguntarle a Jess qué gana. ProbarReglas hace eso con una lista de casos, cada uno con la acción que debería ganar: 

public class ProbarReglas {

    static final String REGLAS = "es/ucm/fdi/ici/c2627/practica3/grupoYY/mspacman-v1.clp";
    static int fallos = 0;

    public static void main(String[] args) throws JessException {
        Rete jess = new Rete();
        jess.batch(REGLAS);
        jess.eval("(watch rules)");           // Jess escribe cada regla que dispara

        caso(jess, "nada cerca: come", "comer",
                "(MSPACMAN (distFantasma 80) (distPPill 40) (ultima comer))");

        caso(jess, "a 25 viniendo de huir: sigue huyendo", "huir",
                "(MSPACMAN (distFantasma 25) (distPPill 40) (ultima huir))");

        caso(jess, "comestible a 5 y otro peligroso a 15: lo remata", "perseguir",
                "(MSPACMAN (distFantasma 15) (distPPill 1000) (ultima huir))",
                "(FANTASMA (nombre PINKY) (comestible true) (distancia 5) (tiempo 100))",
                "(FANTASMA (nombre SUE) (comestible false) (distancia 15) (tiempo 0))");

        // … en el proyecto hay ocho

        System.out.println(fallos == 0 ? "\nTodos los casos bien." : "\n" + fallos + " casos MAL.");
    }

    static void caso(Rete jess, String nombre, String esperada, String... hechos) throws JessException {
        System.out.println("\n--- " + nombre);
        jess.reset();
        for (String h : hechos) jess.assertString(h);
        jess.run();

        Fact gana = null;                       // lo mismo que hace RuleEngine: la de más priority
        for (Iterator<?> it = jess.listFacts(); it.hasNext(); ) {
            Fact f = (Fact) it.next();
            if (f.getName().equals("MAIN::ACTION") && (gana == null
                    || f.getSlotValue("priority").intValue(null) > gana.getSlotValue("priority").intValue(null)))
                gana = f;
        }
        String id = gana == null ? "(ninguna)" : gana.getSlotValue("id").toString();
        boolean bien = id.equals(esperada);
        if (!bien) fallos++;
        System.out.printf("%s  gana %s, esperaba %s%n", bien ? "BIEN" : "MAL ", id, esperada);
    }
}

Se lanza como cualquier main, sin abrir el juego, y tarda menos de un segundo. Esto es lo que saca uno de los casos: 

--- comestible a 5 y otro peligroso a 15: lo remata
FIRE 1 MAIN::sigueElPeligro f-1
FIRE 2 MAIN::peligro f-1
FIRE 3 MAIN::huir f-4
FIRE 4 MAIN::rematar f-2
FIRE 5 MAIN::comer f-1
BIEN  gana perseguir, esperaba perseguir

Las líneas FIRE las escribe Jess por el (watch rules): qué regla se dispara, en qué orden y con qué hechos (f-1 es el primero que se asertó, f-4 el PELIGRO que concluyó sigueElPeligro). Se disparan cinco reglas y se asertan tres ACTION, de huir, rematar y comer; gana el de rematar porque su priority es la más alta. peligro se dispara pero no aserta nada nuevo, porque el PELIGRO ya existía.

Una regla nueva, un caso nuevo

Antes de medir una regla con 300 partidas, escribid el caso para el que la habéis pensado y comprobad que gana. Y no borréis los casos viejos: son la forma de enteraros en un segundo de que una regla nueva ha roto otra. En la regla de cazar del ejemplo, fue un caso de estos el que destapó que cazar se disparaba aunque hubiera peligro, porque la traza enseñaba un FIRE que no debía estar.

Los casos sirven también para el diario: "este caso fallaba, cambié esto y ya no" es exactamente el tipo de entrada que se pide, y se puede comprobar.

03

Ver las reglas mientras se juega

El observador que trae el motor, ConsoleRuleEngineObserver, vuelca en cada turno todos los hechos y el ACTION ganador. Tiene dos problemas: escribe cientos de líneas por segundo, y no dice qué reglas se han disparado, sólo los hechos que han quedado. Una regla que aserta un hecho intermedio, como peligro, o que aserta lo mismo que otra, no deja rastro.

TrazaReglas escucha a la vez al RuleEngine (para saber qué ACTION gana) y a Jess (para saber qué reglas se disparan), y sólo escribe cuando cambia la acción ganadora: 

/**
 * Cuenta qué reglas se disparan en cada turno, qué ACTION gana, y al final
 * cuántas veces se ha disparado cada regla. Sólo para depurar: no la entreguéis
 * enganchada, que imprime mucho y va más lento.
 */
public class TrazaReglas implements JessListener, RuleEngineObserver {

    private final String nombre;
    private final boolean soloCambios;      // true: sólo imprime cuando cambia la acción ganadora
    private final Rete jess;

    private final List<String> esteTurno = new ArrayList<>();
    private final Map<String, Integer> vecesRegla = new TreeMap<>();
    private final Map<String, Integer> vecesGana = new TreeMap<>();
    private String ganadora = "";
    private boolean huboAction = true;
    private int turno = 0;

    public TrazaReglas(String nombre, RuleEngine motor, boolean soloCambios) {
        this.nombre = nombre;
        this.soloCambios = soloCambios;
        this.jess = reteDe(motor);
        motor.addObserver(this);                                  // avisa del ACTION ganador
        jess.addJessListener(this);                               // avisa de cada regla
        jess.setEventMask(jess.getEventMask() | JessEvent.DEFRULE_FIRED | JessEvent.RESET);
        for (Iterator<?> it = jess.listDefrules(); it.hasNext(); ) // todas, para ver las que no salen
            vecesRegla.put(sinModulo(((Defrule) it.next()).getName()), 0);
    }

    /** Jess avisa de cada regla que se dispara y de cada reset (uno por turno). */
    @Override
    public void eventHappened(JessEvent e) throws JessException {
        if (e.getType() == JessEvent.RESET) {
            if (!huboAction)
                System.out.printf("[%s] t=%d  NINGÚN ACTION: devuelve NEUTRAL. Reglas: %s%n",
                        nombre, turno, esteTurno);
            esteTurno.clear();
            huboAction = false;
            turno++;
        } else if (e.getType() == JessEvent.DEFRULE_FIRED) {
            String regla = sinModulo(((Activation) e.getObject()).getRule().getName());
            esteTurno.add(regla);
            vecesRegla.merge(regla, 1, Integer::sum);
        }
    }

    /** El RuleEngine avisa del ACTION ganador, después de run(). */
    @Override
    public void actionFired(String action, Collection<String> facts) {
        huboAction = true;
        String id = slot(action, "id");
        vecesGana.merge(id, 1, Integer::sum);
        if (!soloCambios || !id.equals(ganadora)) {
            System.out.printf("[%s] t=%d  %s → gana %s %s%n", nombre, turno, esteTurno, id, slot(action, "info"));
            for (String f : facts)                                // los candidatos que perdieron
                if (f.startsWith("(MAIN::ACTION") && !f.equals(action))
                    System.out.printf("           pierde %s (%s) %s%n",
                            slot(f, "id"), slot(f, "priority"), slot(f, "info"));
        }
        ganadora = id;
    }

    @Override
    public void ruleEngineReset() { }

    /** Llamadlo al final (por ejemplo en postCompute): las reglas a 0 no existen. */
    public void resumen() {
        System.out.printf("[%s] %d turnos. Veces que se dispara cada regla:%n", nombre, turno);
        vecesRegla.forEach((r, n) -> System.out.printf("   %6d  %s%s%n", n, r, n == 0 ? "   <-- NUNCA" : ""));
        System.out.printf("[%s] Veces que gana cada acción:%n", nombre);
        vecesGana.forEach((a, n) -> System.out.printf("   %6d  %s%n", n, a));
    }

    // ---- utilidades -------------------------------------------------------

    /** El RuleEngine del motor no deja ver su Rete: se lo pedimos por reflexión. */
    private static Rete reteDe(RuleEngine motor) {
        try {
            Field f = RuleEngine.class.getDeclaredField("jess");
            f.setAccessible(true);
            return (Rete) f.get(motor);
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException("No puedo llegar al Rete del RuleEngine", e);
        }
    }

    private static String sinModulo(String regla) {
        return regla.startsWith("MAIN::") ? regla.substring(6) : regla;
    }

    /** El valor de un slot en un hecho escrito como texto: (MAIN::ACTION (id huir) ...). */
    private static String slot(String hecho, String slot) {
        int i = hecho.indexOf("(" + slot + " ");
        if (i < 0) return "";
        i += slot.length() + 2;
        return hecho.substring(i, hecho.indexOf(')', i));
    }
}

Tres cosas de cómo está hecha, por si queréis cambiarla:

  • Jess avisa con eventos. Un JessListener registrado en el Rete recibe un DEFRULE_FIRED por cada regla que se dispara y un RESET por cada reset(), que en el juego es uno por turno. Por eso t cuenta turnos.
  • El Rete se saca por reflexión. El RuleEngine del motor lo guarda en un atributo sin getter, y el motor no se modifica. Leerlo así es una trampa aceptable para depurar, que es lo único para lo que sirve esta clase.
  • El orden en el que llegan los avisos es RESET, después un DEFRULE_FIRED por regla, y al final actionFired. Si un turno llega al siguiente RESET sin actionFired, es que no hubo ningún ACTION.

Engancharla

Al motor que queráis mirar, y sólo a ese. Es lo que hace VerPartida, en el proyecto: 

MsPacMan pacman = new MsPacMan();
TrazaReglas traza = new TrazaReglas("MSPACMAN", pacman.getMotor(), true);   // true: sólo los cambios

executor.runGame(pacman, new GhostsAggressive(), 40);   // 40 ms por turno: más, para verlo despacio
traza.resumen();

Para un fantasma, lo mismo con su motor: new TrazaReglas("PINKY", ghosts.getMotor(GHOST.PINKY), true). Con false escribe todos los turnos; sirve para mirar un momento concreto, no una partida entera.

Leerla

Las primeras líneas de una partida de verdad, con las siete reglas y contra los agresivos:

[MSPACMAN] t=1  [comer] → gana comer "R1: no pasa nada"
[MSPACMAN] t=116  [peligro, huir, comer] → gana huir "R4: hay peligro"
           pierde comer (10) "R1: no pasa nada"
[MSPACMAN] t=222  [sigueElPeligro, peligro, aLaPPill, huir, comer] → gana irAPPill "R5: la PPill está más cerca que él"
           pierde huir (80) "R4: hay peligro"
           pierde comer (10) "R1: no pasa nada"
[MSPACMAN] t=224  [comer, cazar, rematar] → gana perseguir "R7: rematar a PINKY"
           pierde comer (10) "R1: no pasa nada"
           pierde perseguir (60) "R6: cazar a PINKY"
[MSPACMAN] t=262  [comer] → gana comer "R1: no pasa nada"

Se lee como un diario de la partida. Come durante 115 turnos sin cambiar de idea. En el 116 aparece un fantasma a menos de 20, se dispara peligro, que no aserta ningún ACTION pero sí aparece en la lista, y huir le gana a comer. En el 222 tiene la píldora de poder más cerca que el fantasma y va a por ella; dos turnos después se la ha comido, PINKY está comestible a menos de 10, y rematar le gana a cazar, las dos con el mismo id pero distinta razón. A los 262 no queda nada que hacer y vuelve a comer.

Entre corchetes van todas las reglas disparadas en ese turno, por orden. Es lo que no da el observador del motor, y es lo que hace falta para ver un hecho intermedio, una regla que se dispara sin que se note o una que se dispara cuando no debería.

04

El resumen: las reglas que no existen

Al final de la partida, resumen() cuenta cuántas veces se ha disparado cada regla del fichero, también las que no se han disparado nunca, y cuántas veces ha ganado cada acción. Con las siete reglas, tres partidas contra los agresivos: 

[MSPACMAN] 8727 turnos. Veces que se dispara cada regla:
       40  aLaPPill
      276  cazar
     8727  comer
     7260  huir
     7260  peligro
       85  rematar
     7213  sigueElPeligro
[MSPACMAN] Veces que gana cada acción:
     1196  comer
     7220  huir
       40  irAPPill
      271  perseguir

Esto ya dice mucho antes de medir nada. Contra estos rivales, Ms. Pac-Man pasa huyendo más de cuatro de cada cinco turnos. Y aLaPPill se dispara 40 veces en 8 727 turnos, así que ninguna medida va a notar si es buena o mala: es justo lo que salió al medirla.

Ahora el mismo resumen con un error de una letra: en rematar, (comestible TRUE) en vez de (comestible true). Java escribe true en minúsculas, y para Jess son dos símbolos distintos: 

[MSPACMAN] 2182 turnos. Veces que se dispara cada regla:
       20  aLaPPill
      491  cazar
     2182  comer
      686  huir
      686  peligro
        0  rematar   <-- NUNCA
      657  sigueElPeligro

Sin el resumen, esa regla estaría en el fichero, contaría para las quince, y nadie se enteraría de que no hace nada: el juego no da ningún error. Una regla que no se dispara en una partida entera no existe, y lo primero que hay que hacer con ella es averiguar por qué.

Para el diario

El resumen de cada versión, contra el rival que más os preocupa, es una tabla de diez líneas que dice qué reglas trabajan y cuáles no. Pegadlo en el diario junto a las medidas: "esta regla se dispara 40 veces en tres partidas" explica muchos "no se nota".

05

Cuando no gana nadie

Si en un turno ninguna regla aserta un ACTION, el RuleEngine devuelve MOVE.NEUTRAL sin decir nada, y Ms. Pac-Man sigue recta o se queda quieta. La traza lo avisa. Esto es lo que sale si se quita la regla comer: 

[MSPACMAN] t=1  NINGÚN ACTION: devuelve NEUTRAL. Reglas: []
[MSPACMAN] t=2  NINGÚN ACTION: devuelve NEUTRAL. Reglas: []
[MSPACMAN] t=3  NINGÚN ACTION: devuelve NEUTRAL. Reglas: []

La lista de reglas vacía dice que no se disparó ninguna, ni siquiera las intermedias. Las causas habituales, por orden de frecuencia: no hay regla por defecto; los hechos no se han asertado (en la consola, más arriba, habrá un Exception assserting fact); o el .clp no se ha cargado entero (al arrancar, Exception loading rules from file).

06

Sin escribir Java

Si sólo queréis ver un momento qué se dispara, hay dos atajos que no necesitan ninguna clase:

  • (watch rules) en la primera línea del .clp. El RuleEngine lo ejecuta al cargar el fichero, y desde entonces Jess escribe una línea FIRE por cada regla disparada, en todos los turnos, hasta que lo quitéis. Está comprobado con el motor de la asignatura: sobrevive a los reset de cada turno. Con (watch facts) salen también los hechos que entran y salen. Escribe muchísimo: para una partida corta, o para un fantasma solo.
  • La consola de Jess, con el .clp cargado y unos hechos de prueba, como se cuenta en CLIPS y Jess. Es ProbarReglas a mano.

Y en la wiki misma, el banco de pruebas de la guía del ejemplo ejecuta un .clp en el navegador y dice qué ACTION elegiría el motor.

07

Errores típicos de la práctica

Los de Jess con el paquete rules (plantillas que no coinciden, ids que no están en el mapa, TRUE en mayúsculas, empates de priority) están en los apuntes. Estos son los que salieron montando el ejemplo:

Lo que pasaPor qué, y qué hacer
Al medir muchas partidas a la vez, la media de una versión baja de golpe unos cientos de puntos de una tanda a otra, sin cambiar nada. Jess no sabe leer dos .clp a la vez: si dos controladores se crean al mismo tiempo en hilos distintos, uno puede quedarse con media base de reglas (en la consola de errores sale Bad value at token y Exception loading rules from file). Pasa una de cada pocas tandas. Se evita creando cada RuleEngine en el constructor del controlador, nunca en preCompute ni en getMove, y creando los controladores de uno en uno, como hace Comparar.
Las reglas no ven ningún fantasma, y no sale ningún error. Un atributo del Input inicializado en su declaración: se ejecuta después de parseInput y lo vacía. Está en la guía del ejemplo.
Después de cambiar grupoYY por vuestra letra, nada se mueve. Las rutas del .clp son cadenas de texto y el Refactor > Rename no las toca: RULES_PATH y REGLAS.
Una versión vieja deja de funcionar después de añadir un hecho nuevo al Input. Su .clp no tiene la plantilla del hecho nuevo y Jess lo rechaza. Añadidle el deftemplate: no cambia lo que hacía, porque ninguna de sus reglas lo usa.
Una regla se dispara dos veces y su ACTION aparece sólo una. No es un error: Jess no aserta dos hechos idénticos. Pasa con PELIGRO en el ejemplo, que lo concluyen dos reglas. Si necesitáis distinguirlos, que el info sea distinto.
Se dispara una regla con un not que no debería cumplirse. Se disparó antes de que otra regla asertara el hecho que niega. Dad más salience a las reglas que concluyen hechos intermedios: el caso de cazar.
Con ProbarReglas funciona y en el juego no. Los hechos del caso no son los que aserta el Input. Copiad un turno de verdad del ConsoleRuleEngineObserver con true, que escribe todos los hechos, y usadlo como caso.
El concurso o Comparar van muy lentos y la consola no para. Una TrazaReglas, un ConsoleRuleEngineObserver o un (watch rules) olvidado. Detrás de un DEBUG a false, o fuera antes de entregar.
