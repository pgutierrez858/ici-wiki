Ms. Pac-Man con siete reglas El ejemplo guiado de la Práctica 3: de una regla a siete, midiendo cada paso.

Un controlador de reglas completo y pequeño, montado poco a poco: los hechos que ve, las cuatro acciones que sabe hacer y siete reglas que se añaden de una en una, cada una con lo que cambió en 300 partidas contra cinco rivales. Al final, lo que le falta a esta Ms. Pac-Man, y el esqueleto de los fantasmas para que empecéis los vuestros.

Esta página da por leídas dos de los apuntes: CLIPS y Jess, para la sintaxis, y Reglas en Ms. Pac-Man, para el paquete rules del motor. Aquí no se explica qué es un RulesInput: se usa.

02

Lo que ve: los hechos

Para decidir, a esta Ms. Pac-Man le bastan tres números sobre ella y un hecho por cada fantasma que esté fuera de la cárcel. Un turno cualquiera, tal y como llega a Jess: 

(FANTASMA (nombre PINKY) (comestible true) (distancia 30) (tiempo 100))
(FANTASMA (nombre SUE) (comestible false) (distancia 15) (tiempo 0))
(MSPACMAN (distFantasma 15) (distPPill 40) (ultima comer))

Todo lo que necesita caminos o bucles se calcula en Java, en parseInput, y a Jess le llega ya hecho. Las reglas sólo comparan números y símbolos: 

public class MsPacManInput extends RulesInput {

    private static final int LEJOS = 1000;        // "no hay": ningún fantasma, ninguna píldora

    private int distFantasma;                     // al fantasma peligroso más cercano
    private int distPPill;                        // a la píldora de poder más cercana
    private List<String> fantasmas;               // un hecho FANTASMA por cada uno fuera de la cárcel
    private final String ultima;                  // la acción que ganó en el turno anterior

    public MsPacManInput(Game game, String ultima) {
        super(game);                              // llama a parseInput()
        this.ultima = ultima;
    }

    @Override
    public void parseInput() {
        int pacman = game.getPacmanCurrentNodeIndex();
        distFantasma = LEJOS;
        fantasmas = new ArrayList<>();
        for (GHOST g : GHOST.values()) {
            if (game.getGhostLairTime(g) > 0) continue;      // en la cárcel no cuenta
            int nodo = game.getGhostCurrentNodeIndex(g);
            boolean comestible = game.isGhostEdible(g);
            // peligroso: lo que tarda él en llegar a mí, que no puede dar la vuelta
            // comestible: lo que tardo yo en llegar a él
            int d = comestible
                    ? game.getShortestPathDistance(pacman, nodo)
                    : game.getShortestPathDistance(nodo, pacman, game.getGhostLastMoveMade(g));
            if (!comestible) distFantasma = Math.min(distFantasma, d);
            fantasmas.add(String.format("(FANTASMA (nombre %s) (comestible %s) (distancia %d) (tiempo %d))",
                    g, comestible, d, game.getGhostEdibleTime(g)));
        }
        distPPill = LEJOS;
        for (int ppill : game.getActivePowerPillsIndices())
            distPPill = Math.min(distPPill, game.getShortestPathDistance(pacman, ppill));
    }

    @Override
    public Collection<String> getFacts() {
        List<String> facts = new ArrayList<>(fantasmas);
        facts.add(String.format("(MSPACMAN (distFantasma %d) (distPPill %d) (ultima %s))",
                distFantasma, distPPill, ultima));
        return facts;
    }
}

Tres decisiones de diseño que conviene ver:

  • Las dos distancias no se miden igual. La de un fantasma peligroso se mide desde él y con su último movimiento, porque un fantasma no puede dar media vuelta: lo que importa es cuánto tarda él en llegar. La de uno comestible, desde Ms. Pac-Man, porque ahí la que se mueve hacia el otro es ella. Es lo mismo que en la Práctica 1.
  • "No hay" es un número grande, no un hueco. Jess no tiene null. Con LEJOS = 1000, una regla que pregunta (< ?d 20) funciona igual haya o no fantasmas, sin un caso aparte.
  • Los fantasmas de la cárcel no se asertan. Para las reglas no existen, y así ninguna tiene que acordarse de excluirlos.
Un error de Java que parece de Jess

El constructor de RulesInput llama a parseInput() antes de que se inicialicen los atributos de la subclase. Si escribís private List<String> fantasmas = new ArrayList<>(); en la declaración, esa línea se ejecuta después de parseInput y borra lo que había rellenado: las reglas no ven ningún fantasma y no sale ningún error. Los atributos que rellena parseInput se declaran sin valor.

03

Lo que sabe hacer: cuatro acciones

idClaseQué hace
comerComerActionHacia la píldora normal más cercana; si no quedan, hacia la de poder.
huirHuirActionLejos del fantasma peligroso más cercano.
irAPPillIrAPPillActionHacia la píldora de poder más cercana.
perseguirPerseguirActionHacia el fantasma que diga la regla, en el slot fantasma del ACTION.

Las tres primeras son métodos de la Práctica 1 metidos en una clase. La cuarta es la interesante, porque tiene un parámetro: no sabe a quién perseguir hasta que se lo dice la regla que la ha elegido. Lo lee en parseFact, que el motor llama justo antes de execute: 

public class PerseguirAction implements RulesAction {

    private GHOST presa;

    @Override
    public void parseFact(Fact actionFact) {
        try {
            presa = GHOST.valueOf(actionFact.getSlotValue("fantasma").stringValue(null));
        } catch (JessException | IllegalArgumentException e) {
            presa = null;                          // la regla no dijo a quién
        }
    }

    @Override
    public MOVE execute(Game game) {
        if (presa == null) return MOVE.NEUTRAL;
        return game.getNextMoveTowardsTarget(game.getPacmanCurrentNodeIndex(),
                game.getGhostCurrentNodeIndex(presa), DM.PATH);
    }

    @Override
    public String getActionId() { return "perseguir"; }
}

Una acción con parámetro ahorra clases: en vez de PerseguirBlinky, PerseguirInky… hay una, y la regla dice cuál. Lo mismo vale para "ir a un nodo", "huir por una salida" o "esperar junto a una píldora".

04

Siete reglas, de una en una

Las reglas se escribieron en este orden, y después de cada paso se midió la versión nueva contra la anterior con Comparar, contra los fantasmas de referencia que trae el proyecto. Al final de cada paso va, en una línea, qué cambió.

El fichero empieza con las plantillas. Las dos primeras son las de los hechos del Input; PELIGRO es un hecho que no viene de Java, sino de las propias reglas, y ACTION lleva el slot fantasma para la acción con parámetro: 

(deftemplate MSPACMAN
   (slot distFantasma (type NUMBER))   ; al peligroso más cercano; 1000 si no hay
   (slot distPPill    (type NUMBER))   ; a la PPill más cercana; 1000 si no quedan
   (slot ultima       (type SYMBOL)))  ; la acción que ganó el turno anterior

(deftemplate FANTASMA
   (slot nombre     (type SYMBOL))     ; BLINKY, INKY, PINKY, SUE
   (slot comestible (type SYMBOL))     ; true o false, en minúsculas, como Java
   (slot distancia  (type NUMBER))
   (slot tiempo     (type NUMBER)))    ; turnos que le quedan de comestible

(deftemplate PELIGRO)                  ; un hecho intermedio: lo asertan unas reglas y lo leen otras

(deftemplate ACTION
   (slot id) (slot info (default "")) (slot priority (type NUMBER))
   (slot fantasma (type SYMBOL)))      ; el parámetro de "perseguir"
1

Comer, si no pasa nada más

;; R1 · si no pasa nada más, comer
(defrule comer
   (MSPACMAN)
   =>
   (assert (ACTION (id comer) (info "R1: no pasa nada") (priority 10))))

(MSPACMAN) sin slots se cumple con cualquier hecho MSPACMAN, o sea, en todos los turnos. Es la regla por defecto: siempre hay un ACTION, y con priority 10 cualquier otra le gana. Sin una regla así, el turno en que no se cumpla ninguna otra Ms. Pac-Man recibe MOVE.NEUTRAL.

Al medirla: unos 2 250 puntos de media. Es la Ms. Pac-Man de la Práctica 0 que sólo come, y la línea base de todo lo demás.

2

Huir, con un hecho intermedio

;; R2 · un fantasma peligroso a menos de 20 es peligro
(defrule peligro
   (declare (salience 10))             ; antes que las que preguntan por PELIGRO (paso 5)
   (MSPACMAN (distFantasma ?d&:(< ?d 20)))
   =>
   (assert (PELIGRO)))

;; R4 · con peligro, huir
(defrule huir
   (PELIGRO)
   =>
   (assert (ACTION (id huir) (info "R4: hay peligro") (priority 80))))

Se podría escribir en una sola regla, "si hay un fantasma a menos de 20, huir". Se parte en dos porque "estar en peligro" es una conclusión que van a usar varias reglas: huir ahora, y en los pasos siguientes aLaPPill, que también la necesita, y cazar, que necesita que no se cumpla. Y porque va a haber dos formas de llegar a ella (la del paso 3). Es el encadenamiento hacia delante de los apuntes: una regla aserta un hecho que dispara otra.

Al medirlo: vive bastante más, una vida cada 470 turnos en vez de cada 330, pero no hace más puntos, porque huyendo no come. Mirando sólo los puntos parecería que no ha cambiado nada: por eso conviene medir más de una cosa.

3

Recordar el turno anterior: histéresis

;; R3 · si ya venía huyendo, sigue siendo peligro hasta los 30
(defrule sigueElPeligro
   (declare (salience 10))
   (MSPACMAN (ultima huir) (distFantasma ?d&:(< ?d 30)))
   =>
   (assert (PELIGRO)))

Con un solo umbral, un fantasma que ronda los 20 nodos hace que Ms. Pac-Man cambie de idea cada pocos turnos. La solución es la histéresis de la Práctica 2, entrar a 20 y salir a 30, pero una base de reglas no se acuerda del turno anterior: el motor vacía la memoria en cada turno. Así que la memoria vive en Java y llega como un hecho más, el slot ultima.

¿Quién apunta qué acción ganó? Un observador del motor, que es lo único que se entera del ACTION ganador sin tocar las acciones: 

/** Se apunta el id del ACTION que gana en cada turno, para dárselo al Input del siguiente. */
public class UltimaAccion implements RuleEngineObserver {

    private String id = "nada";

    public String get() { return id; }

    public void olvidar() { id = "nada"; }      // al empezar cada partida

    @Override
    public void actionFired(String action, Collection<String> facts) {
        // action es el hecho ganador como texto: (MAIN::ACTION (id huir) (info "...") ...)
        int i = action.indexOf("(id ") + 4;
        id = action.substring(i, action.indexOf(')', i));
    }

    @Override
    public void ruleEngineReset() { }
}

Al medirla: no se nota. Con esta forma de huir, cambiar de idea a los 20 nodos no le costaba vidas. Se queda porque es el ejemplo de cómo recordar entre turnos; en vuestro diario, algo así se apunta tal cual: "no se nota, y la dejo por esto".

4

Comparar dos slots: ir a la píldora de poder

;; R5 · con peligro, si la píldora de poder está más cerca que el fantasma, a por ella
(defrule aLaPPill
   (PELIGRO)
   (MSPACMAN (distFantasma ?f) (distPPill ?p&:(< ?p ?f)))
   =>
   (assert (ACTION (id irAPPill) (priority 90)
                   (info "R5: la PPill está más cerca que él"))))

La condición compara dos slots del mismo hecho: ?f se liga a la distancia del fantasma y la restricción de distPPill la usa. Y su priority 90 le gana a la de huir, que también se aserta en ese turno: las dos se disparan, y el RuleEngine se queda con la más alta.

Al medirla: tampoco se nota, y la traza dice por qué: en tres partidas contra los agresivos se dispara 40 veces, frente a las 7 260 de huir. Una regla que casi nunca se cumple no puede cambiar mucho, por buena idea que sea. Antes de darle vueltas a si está bien, hay que mirar si se dispara.

5

Cazar: not, variables y un parámetro

;; R6 · sin peligro, a por el comestible más cercano, si llego antes de que se le pase
(defrule cazar
   (not (PELIGRO))
   (FANTASMA (nombre ?g) (comestible true)
             (distancia ?d) (tiempo ?t&:(> ?t ?d)))
   (not (FANTASMA (comestible true) (distancia ?d2&:(< ?d2 ?d))))
   =>
   (assert (ACTION (id perseguir) (fantasma ?g) (priority 60)
                   (info (str-cat "R6: cazar a " ?g)))))

Es la regla con más cosas nuevas, línea a línea:

  • (not (PELIGRO)): sólo si ninguna regla ha concluido que hay peligro.
  • El segundo patrón liga tres variables de un mismo fantasma: su nombre, su distancia y su tiempo de comestible, y exige que el tiempo pase de la distancia, para llegar antes de que se recupere.
  • El tercero es la forma de decir "el más cercano" en CLIPS: que no haya otro comestible más cerca que él. Con dos comestibles, la regla se cumple sólo para el de menor distancia.
  • (fantasma ?g) le pasa el nombre a PerseguirAction, que lo lee en parseFact.

Y con este not aparece un problema de orden. Si Jess dispara cazar antes que peligro, en ese momento todavía no hay PELIGRO y cazar se cumple. Con un fantasma comestible a 30 y otro peligroso a 15, sin salience, la traza de Jess sale así: 

FIRE 1 MAIN::cazar f-0,, f-2,
FIRE 2 MAIN::comer f-1
FIRE 3 MAIN::peligro f-1
FIRE 4 MAIN::huir f-6

Aquí gana huir igualmente, porque tiene más priority, pero de chiripa: ha llegado a asertarse un perseguir que no debía existir. Con (declare (salience 10)) en las dos reglas que concluyen PELIGRO, Jess las dispara siempre antes, y cazar ni siquiera entra: 

FIRE 1 MAIN::peligro f-1
FIRE 2 MAIN::huir f-4
FIRE 3 MAIN::comer f-1

La regla general: las reglas que asertan hechos intermedios van con más salience que las que los leen. Es el único uso de salience que necesitáis; para elegir entre acciones ya está priority.

Al medirla: el salto grande. Pasa de unos 2 150 puntos a unos 2 950, mejora contra todos los rivales y se come más del doble de fantasmas.

6

Rematar, y una regla que no sirve

;; R7 · un comestible a menos de 10 se remata, aunque haya peligro
(defrule rematar
   (FANTASMA (nombre ?g) (comestible true)
             (distancia ?d&:(< ?d 10)) (tiempo ?t&:(> ?t ?d)))
   =>
   (assert (ACTION (id perseguir) (fantasma ?g) (priority 85)
                   (info (str-cat "R7: rematar a " ?g)))))

La idea parece buena: con un comestible a menos de 10 nodos, comérselo vale más que huir. Su priority 85 la deja entre huir (80) y aLaPPill (90), que es justo lo que dice esa frase.

Al medirla: no cambia nada, ni repitiendo la medida con otras partidas. Así que la versión buena es la de seis reglas: con lo mismo, es más sencilla. En el proyecto, mspacman-v0.clp son las seis primeras y mspacman-v1.clp las siete.

De seis pasos, dos cambiaron algo, y sólo uno subió los puntos. Es lo normal: sin medir, los seis habrían parecido mejoras, porque todos tenían una buena razón. Cómo se mide y cómo se sabe si una diferencia es de verdad está en Comparar versiones.

05

El controlador

public class MsPacMan extends PacmanController {

    private static final String RULES_PATH = "es/ucm/fdi/ici/c2627/practica3/grupoYY/";

    private final RuleEngine motor;
    private final UltimaAccion ultima = new UltimaAccion();

    public MsPacMan() {
        this("mspacman-v1.clp");                 // la versión que va al concurso
    }

    /** Cada versión, un .clp distinto, con el mismo Input y las mismas acciones. */
    public MsPacMan(String ficheroReglas) {
        setName("MsPacMan YY");
        setTeam("Grupo YY");

        HashMap<String, RulesAction> acciones = new HashMap<>();
        for (RulesAction a : new RulesAction[] {
                new ComerAction(), new HuirAction(),
                new IrAPPillAction(), new PerseguirAction() })
            acciones.put(a.getActionId(), a);

        motor = new RuleEngine("MSPACMAN", RULES_PATH + ficheroReglas, acciones);
        motor.addObserver(ultima);
    }

    /** Para engancharle la TrazaReglas desde fuera. */
    public RuleEngine getMotor() { return motor; }

    @Override
    public void preCompute(String rival) {
        ultima.olvidar();
    }

    @Override
    public MOVE getMove(Game game, long timeDue) {
        MsPacManInput input = new MsPacManInput(game, ultima.get());
        motor.reset();
        motor.assertFacts(input.getFacts());
        return motor.run(game);
    }
}
  • El mapa de acciones se rellena con getActionId(), no escribiendo el id a mano otra vez: así el id sólo está escrito en dos sitios, la acción y las reglas, y no en tres.
  • Cada versión es un .clp. El constructor sin argumentos apunta a la que va al concurso; el otro sirve para que Comparar juegue con cualquiera de ellas sin duplicar clases. Si una versión necesita un hecho o una acción nuevos, ved cómo organizar las versiones.
  • El RuleEngine se crea en el constructor, y en ningún otro sitio. Jess no sabe leer dos .clp a la vez, y el concurso juega en paralelo: crearlo en preCompute o en el primer getMove puede romper la carga de las reglas sin que os enteréis. Está contado en Depurar reglas.
  • preCompute se llama antes de cada partida: ahí se olvida la memoria de la anterior.

Cómo organizar las versiones

Con reglas, lo normal es que de una versión a otra sólo cambie el .clp. Entonces basta con un fichero por versión y nada más: 

es/ucm/fdi/ici/c2627/practica3/grupoYY/
├── MsPacMan.java          // MsPacMan() → "mspacman-v2.clp", la del concurso
├── mspacman-v0.clp
├── mspacman-v1.clp
├── mspacman-v2.clp
├── Ghosts.java            // Ghosts() → "ghosts-v1.clp"
├── ghosts-v0.clp
├── ghosts-v1.clp
├── mspacman/  MsPacManInput.java  actions/
└── ghosts/    GhostsInput.java    actions/

Si una versión necesita un hecho nuevo, el Input lo aserta para todas, así que su deftemplate tiene que estar también en los .clp anteriores; sin él, Jess rechaza el hecho y lo dice en la consola. Añadir la plantilla no cambia lo que hacían, porque ninguna de sus reglas lo mira. Si necesita una acción nueva, se añade al mapa: las versiones viejas no la asertan nunca. Lo que no vale es cambiar lo que hace una acción o un hecho que ya usaban las versiones anteriores, porque entonces sus medidas dejan de ser suyas.

06

Seguir con Ms. Pac-Man

Siete reglas, y tres de ellas no se notan: este controlador es un punto de partida, no una solución. Si lo veis jugar un rato con VerPartida, sus fallos saltan a la vista:

Lo que hace malPor quéPor dónde atacarlo
Huye hacia otro fantasma, o hacia un callejón. HuirAction sólo mira el fantasma más cercano. Un hecho que diga por qué salidas del próximo cruce llega antes que todos, y reglas que elijan una. La Práctica 1 tiene medio trabajo hecho.
Come hacia un fantasma que viene de frente. comer va a la píldora más cercana, esté donde esté. Una acción comer con parámetro, por ejemplo la zona, y reglas que elijan zonas tranquilas. Un mapa de influencia da ese hecho.
Gasta las píldoras de poder al pasar. Ninguna regla dice qué hacer cerca de una píldora de poder sin peligro. Reglas para esperar junto a ella hasta tener fantasmas cerca, o para no pisarla.
Persigue a un comestible que se está acabando. tiempo > distancia no cuenta con que el fantasma también se mueve. Un margen, o un hecho calculado en Java: "llego antes de que se recupere".
Huye mucho y no gana puntos huyendo. Mientras huye no come, y contra los agresivos huye en cuatro de cada cinco turnos. Huir hacia donde quedan píldoras, o un umbral de peligro que dependa de si el fantasma viene hacia ella o se aleja.

Cómo crecer sin perder el control

  • Primero el hecho, después las reglas. La mayoría de las reglas buenas salen de un hecho nuevo bien calculado en Java. Si una condición os obliga a escribir una regla muy larga, probablemente falta un hecho.
  • Una regla, un motivo. Y ese motivo en el info, empezando por el nombre de la regla: es lo que vais a leer en la traza cuando algo salga mal.
  • Prioridades por franjas, para no tener que renumerar todo cada vez que añadís una:
priorityPara quéEn el ejemplo
0 a 19Lo que se hace cuando no pasa nadacomer 10
20 a 59Oportunidades: cosas que conviene hacer si no hay prisalibre
60 a 79Ataquecazar 60
80 a 99Supervivencia, y las excepciones que valen más que sobrevivirhuir 80, rematar 85, aLaPPill 90
  • Cada regla nueva, con su caso. Antes de medirla, una línea en ProbarReglas con la situación para la que la escribís y la acción que debería ganar. Si un cambio posterior la rompe, os enteráis en un segundo y no después de 300 partidas.
  • Y cada versión, medida. Un cambio por versión, contra los mismos rivales, como en la Práctica 2. Ya habéis visto en la tabla de arriba cuántas ideas buenas no se notan.
Qué hace que una base de reglas sea más rica

Para llegar a las 15 reglas que pide la práctica no sirve copiar una regla cambiando el número. Lo que de verdad usa lo que tiene un sistema de reglas, y lo que más se nota al leerlo, son las cosas que han ido apareciendo en esta página: hechos intermedios que encadenan reglas, memoria entre turnos, not, variables que relacionan varios hechos, acciones con parámetros y salience sólo donde hace falta y con su porqué.

Seguir con los fantasmas

Los fantasmas tienen una dificultad que Ms. Pac-Man no tiene: son cuatro, y cada uno necesita su motor de reglas, porque cada uno elige su propio ACTION. Hay dos formas de organizarlo:

FormaCómo esCuándo conviene
Un .clp por fantasma La de la plantilla y los apuntes: blinkyrules.clp, inkyrules.clp…, ids como BLINKYchases y un mapa compartido. Si cada fantasma va a tener una personalidad distinta, con reglas que no comparten.
Una base para los cuatro La de este ejemplo: un solo .clp, un mapa de acciones por fantasma con ids genéricos, y un hecho (YO (nombre BLINKY)) que le dice a cada motor quién es. Si los cuatro piensan igual, o casi: las diferencias se escriben como reglas que preguntan por YO.

Las dos valen. Con la primera es muy fácil acabar con cuatro copias del mismo fichero, y entonces cuentan como uno; con la segunda, las copias no existen. El esqueleto del proyecto usa la segunda: 

public Ghosts(String ficheroReglas) {
    setName("Ghosts YY");
    setTeam("Grupo YY");
    for (GHOST g : GHOST.values()) {
        HashMap<String, RulesAction> acciones = new HashMap<>();   // las de ESTE fantasma
        for (RulesAction a : new RulesAction[] { new PerseguirAction(g), new HuirAction(g) })
            acciones.put(a.getActionId(), a);
        motores.put(g, new RuleEngine(g.name(), RULES_PATH + ficheroReglas, acciones));
    }
}

@Override
public EnumMap<GHOST, MOVE> getMove(Game game, long timeDue) {
    GhostsInput input = new GhostsInput(game);               // una vez para los cuatro
    EnumMap<GHOST, MOVE> movimientos = new EnumMap<>(GHOST.class);
    for (GHOST g : GHOST.values()) {
        if (!game.doesGhostRequireAction(g)) continue;       // fuera de los cruces no hay nada que decidir
        RuleEngine motor = motores.get(g);
        motor.reset();
        motor.assertFacts(input.getFacts());
        motor.assertFacts(List.of("(YO (nombre " + g + "))"));
        movimientos.put(g, motor.run(game));
    }
    return movimientos;
}

Cada fantasma tiene sus propias instancias de PerseguirAction y HuirAction, que saben de qué fantasma son, así que el id puede ser el mismo para los cuatro: perseguir en el motor de Blinky ejecuta la acción de Blinky. Y como un fantasma sólo puede cambiar de dirección en los cruces, fuera de ellos ni se llama a Jess: ahorra la mayor parte del tiempo.

Las reglas del esqueleto, en ghosts-v1.clp. La v0 es lo mismo sin G3, para tener dos versiones que comparar desde el principio: 

(deftemplate FANTASMA
   (slot nombre (type SYMBOL)) (slot comestible (type SYMBOL))
   (slot enCarcel (type SYMBOL)) (slot distPacman (type NUMBER)))
(deftemplate MSPACMAN (slot distPPill (type NUMBER)))
(deftemplate YO (slot nombre (type SYMBOL)))          ; distinto en cada motor: quién soy yo
(deftemplate ACTION (slot id) (slot info (default "")) (slot priority (type NUMBER)))

;; G1 · si no soy comestible, perseguir
(defrule perseguir
   (YO (nombre ?yo))
   (FANTASMA (nombre ?yo) (comestible false))
   =>
   (assert (ACTION (id perseguir) (info "G1: no soy comestible") (priority 10))))

;; G2 · si soy comestible, huir
(defrule huirComestible
   (YO (nombre ?yo))
   (FANTASMA (nombre ?yo) (comestible true))
   =>
   (assert (ACTION (id huir) (info "G2: soy comestible") (priority 50))))

;; G3 · si Ms. Pac-Man está junto a una píldora de poder, no acercarse
(defrule huirDeLaPPill
   (MSPACMAN (distPPill ?d&:(< ?d 15)))
   =>
   (assert (ACTION (id huir) (priority 40)
                   (info "G3: Ms. Pac-Man junto a una PPill"))))

Fijaos en el patrón de G1 y G2: ?yo se liga en YO y se exige en FANTASMA, así que cada motor razona sobre su propio fantasma aunque vea los cuatro hechos. Los otros tres siguen ahí, y eso es lo que permite coordinarse.

Al medirlas, con Comparar en modo fantasmas, la diferencia entre la v0 y la v1 es pequeña: G3 quizá conceda algo menos de puntos, pero harían falta muchas más partidas para asegurarlo. Así son casi todas las mejoras de un controlador que ya funciona.
