Ms. Pac-Man con siete reglas borrosas El ejemplo guiado de la Práctica 4: de dos reglas a siete, midiendo cada paso.

Un controlador borroso completo y pequeño, montado poco a poco: las tres distancias que mide, las cuatro acciones que sabe hacer y siete reglas que se añaden por pasos, cada uno con lo que cambió en 300 partidas contra cinco rivales. Al final, lo que le falta a esta Ms. Pac-Man, y el esqueleto de los fantasmas para que empecéis los vuestros.

Antes de esta guía, leed dos páginas de los apuntes: Inferencia borrosa, para entender qué hace el motor con las reglas, y Lógica borrosa en Ms. Pac-Man, para el formato FCL y el paquete fuzzy del motor. Aquí se usan FuzzyInput, FuzzyEngine y ActionSelector sin volver a explicar qué son.

02

Lo que ve: las entradas

A un sistema borroso sólo le llegan números, uno por variable de entrada. A esta Ms. Pac-Man le bastan tres distancias, en pasos de camino:

VariableQué mide
peligroAl fantasma peligroso más cercano: ni comestible ni en la cárcel.
comestibleAl fantasma comestible más cercano.
ppillA la píldora de poder más cercana.

Todas se calculan en Java, en parseInput, y llegan al FCL en un mapa cuyas claves son los nombres de VAR_INPUT: 

public class MsPacManInput extends FuzzyInput {

    public static final double LEJOS = 150;

    private double peligro, comestible, ppill;

    public MsPacManInput(Game game) {
        super(game);                               // llama a parseInput()
    }

    @Override
    public void parseInput() {
        int yo = game.getPacmanCurrentNodeIndex();
        peligro = LEJOS;
        comestible = LEJOS;
        for (GHOST g : GHOST.values()) {
            if (game.getGhostLairTime(g) > 0) continue;
            double d = game.getShortestPathDistance(yo, game.getGhostCurrentNodeIndex(g));
            if (game.isGhostEdible(g)) comestible = Math.min(comestible, d);
            else peligro = Math.min(peligro, d);
        }
        ppill = LEJOS;
        for (int p : game.getActivePowerPillsIndices())
            ppill = Math.min(ppill, game.getShortestPathDistance(yo, p));
    }

    @Override
    public HashMap<String, Double> getFuzzyValues() {
        HashMap<String, Double> vars = new HashMap<>();   // la clave = el nombre en VAR_INPUT
        vars.put("peligro", peligro);
        vars.put("comestible", comestible);
        vars.put("ppill", ppill);
        return vars;
    }
}

Tres decisiones de diseño que conviene ver:

  • "No hay" es LEJOS, y todo se recorta a 150. Con Jess daba igual que fuera 1000. Aquí no: un término por puntos se queda con el valor del extremo fuera de su rango, así que un -1 valdría "cerca" con un 1. Y los términos se dibujan entre 0 y 150, así que lo que sobra no aporta nada.
  • Una variable por concepto, no por fantasma. El ejemplo del curso pasado tenía BLINKYdistance, PINKYdistance…, y cuatro reglas casi iguales para cada cosa. Con "el peligroso más cercano" basta una. Si alguna decisión necesita mirar a dos fantasmas a la vez (que haya uno a cada lado, por ejemplo), eso se calcula en Java y llega como otra variable.
  • Todas las entradas, en todos los turnos. Una variable a la que no le dais valor en un turno se queda con el del anterior, sin avisar. Por eso parseInput empieza poniendo cada una a LEJOS.
Un error de Java que parece del motor

Como en la Práctica 3, el constructor de FuzzyInput llama a parseInput() antes de que se inicialicen los atributos de la subclase. Si escribís private double peligro = LEJOS; en la declaración, esa línea se ejecuta después y pisa lo que había calculado parseInput: el fantasma siempre está lejos y no sale ningún error. Los atributos que rellena parseInput se declaran sin valor.

03

Lo que sabe hacer: las acciones

getActionId()ClaseQué hace
comerComerActionHacia la píldora normal más cercana; si no quedan, hacia la de poder.
huirHuirActionLejos del fantasma peligroso más cercano.
perseguirPerseguirActionHacia el fantasma comestible más cercano.
irAPPillIrAPPillActionHacia la píldora de poder más cercana.

Son las de la Práctica 3, ahora implementando Action en vez de RulesAction: sin parseFact, porque un FCL no puede pasar parámetros. Por eso perseguir ya no recibe a quién perseguir y va a por el comestible más cercano.

El sistema borroso no elige una acción: devuelve un número por cada variable de salida. Quien elige es el ActionSelector. Éste es el del ejemplo: 

/** Una variable de salida por acción, con el nombre de su getActionId(), y gana la más alta. */
public class MaxActionSelector implements ActionSelector {

    private final Action[] acciones;

    public MaxActionSelector(Action[] acciones) { this.acciones = acciones; }

    @Override
    public Action selectAction(HashMap<String, Double> salidas) {
        Action mejor = null;
        double max = Double.NEGATIVE_INFINITY;
        for (Action a : acciones) {             // en el orden del array, no en el del HashMap
            Double v = salidas.get(a.getActionId());
            if (v != null && v > max) { max = v; mejor = a; }
        }
        return mejor;
    }
}
  • El nombre de cada VAR_OUTPUT es el getActionId() de su acción. Es lo único que une el FCL con Java. Una salida sin acción se ignora, y una acción sin salida no gana nunca.
  • Los empates los gana la que va antes en el array. El de la plantilla del curso pasado recorría el HashMap de salidas, y con dos salidas iguales ganaba cualquiera de las dos según el orden interno del mapa. Aquí el orden lo decidís vosotros: comer va primero, así que en un empate Ms. Pac-Man come. Mejor aún es que no haya empates, y en el paso 2 veréis cómo.
  • Cada acción tiene un toString() que devuelve su id. El FuzzyEngine avisa a los observadores con el toString() de la acción ganadora; sin él, la traza diría HuirAction@5e9f23b4.

Comparar números de salidas distintas sólo tiene sentido si están en la misma escala. Las cuatro van de 0 a 10, con los mismos tres términos: 

DEFUZZIFY huir                       // y lo mismo para comer, perseguir e irAPPill
   TERM poco  := (0, 1) (4, 0);
   TERM algo  := trian 2 5 8;
   TERM mucho := (6, 0) (10, 1);
   METHOD : COG;
   DEFAULT := 0;                     // si no se activa ninguna regla: no me conviene
END_DEFUZZIFY

Con un término activo del todo, poco sale 1,3, algo 5 y mucho 8,7. Son los números que vais a ver una y otra vez en las trazas.

04

Siete reglas, paso a paso

Las reglas se escribieron en este orden, y después de cada paso se midió la versión nueva contra la anterior con Comparar, 300 partidas contra cada uno de los cinco fantasmas de referencia. Al final de cada paso va qué cambió.

Las tres entradas usan los mismos términos. media se solapa con las otras dos, para que no haya distancias en las que no valga nada ningún término: 

FUZZIFY peligro                      // y lo mismo para comestible y ppill
   TERM cerca := (0, 1) (15, 1) (35, 0);
   TERM media := trian 20 45 70;
   TERM lejos := (55, 0) (80, 1) (150, 1);
END_FUZZIFY
1

Dos reglas: huir o comer

RULE 1 : IF peligro IS cerca THEN huir IS mucho;
RULE 2 : IF peligro IS NOT cerca THEN comer IS mucho;

Lo mínimo que juega: huir si el fantasma está cerca, comer si no. NOT es 1−μ1 - \mu1−μ, así que las dos reglas se reparten el peso: a 25 pasos, cerca vale 0,5 y las dos se activan con 0,5.

Y aquí aparece la trampa del término solo. Cada salida tiene un único término activo, mucho, y su centro de gravedad casi no se mueve con el grado: entre 8 y 8,7. Así que gana la regla que se active con más grado, que es como decir "huir si el fantasma está a menos de 25". Dos reglas borrosas con un término cada una son un umbral nítido, el mismo de la Práctica 3.

Al medirlas: unos 2 080 puntos de media y una vida cada 460 turnos. Es la línea base de todo lo demás.

2

Cada salida, por toda su escala

// huir crece al acercarse el fantasma; comer, al alejarse
RULE 1 : IF peligro IS cerca THEN huir IS mucho;
RULE 2 : IF peligro IS lejos THEN huir IS poco;
RULE 3 : IF peligro IS cerca THEN comer IS poco;
RULE 4 : IF peligro IS media THEN comer IS algo;
RULE 5 : IF peligro IS lejos THEN comer IS mucho;

Ahora cada salida tiene reglas para varios términos, así que su valor sí se mueve con la distancia. ProbarBorroso dibuja la curva de control, lo que sale para cada distancia al fantasma con todo lo demás lejos:

Dos cosas que se ven en la tabla. Que comer va subiendo poco a poco a medida que el fantasma se aleja, que es lo que buscábamos. Y que huir cae de 8,2 a 0 de golpe entre 30 y 35: no hay ninguna regla de huir para media, y en ese tramo sale el DEFAULT. Aquí no molesta, porque a esa distancia queremos comer, pero es el tipo de hueco que conviene buscar en vuestras curvas.

Fijaos también en que no hay empates: en ninguna distancia valen lo mismo huir y comer. Una primera versión de este paso tenía IF peligro IS media THEN huir IS algo, comer IS algo, y con el fantasma a 45 las dos salían 5,0 exactos. Ganaba la que fuera primero en el array. ProbarBorroso lo pilló con el caso "peligroso a 45: todavía come".

Al medirlo: 107 puntos más de media, con un umbral de 75. Pasa por poco, así que se repitió con otras 300 semillas: 132 más, con un umbral de 75. Se queda. Contra cada rival por separado casi no se nota; sólo la media, con sus cinco rivales, tiene precisión para verlo.

3

Perseguir: una regla que baja otra salida

// un comestible cerca y ningún peligro encima: perseguirlo, y comer baja
RULE 6 : IF comestible IS cerca AND peligro IS NOT cerca THEN perseguir IS mucho, comer IS poco;

Una regla puede dar valor a varias salidas, y ésta lo aprovecha. Sin peligro, comer vale 8,7 por la regla 5, y perseguir IS mucho sólo, también 8,7: otro empate. Al añadir comer IS poco, la salida comer mezcla mucho y poco, su centro de gravedad baja a 5 y perseguir gana con claridad.

Es la forma borrosa de decir "esto es más importante que aquello". En Jess lo hacía la priority; aquí, una regla que sube una salida y baja la otra.

Al medirla: el salto grande. Pasa de unos 2 190 puntos a unos 2 750, mejora contra los cinco rivales y se come casi el doble de fantasmas, de 1,6 a 2,9 por partida. Es la mspacman-v0.fcl del proyecto: seis reglas.

4

La píldora de poder, y un NOT más ancho de lo que parece

// un fantasma que no está lejos y la píldora de poder cerca: a por ella, y huir baja
RULE 7 : IF peligro IS NOT lejos AND ppill IS cerca THEN irAPPill IS mucho, huir IS poco;

La misma idea que en la Práctica 3: con un fantasma cerca, si la píldora de poder está a mano, mejor ir a por ella que huir. Y el mismo truco que en el paso anterior para que irAPPill le gane a huir.

Al medirla: en la media, ruido (27 puntos, con un umbral de 114). Repitiendo con otras semillas salió mejor por 5 puntos sobre el umbral, que no es una mejora que uno se pueda creer. Lo interesante está en los rivales: en las dos tandas, mejor contra Random y peor contra Avanzado; contra los otros tres cambia de una tanda a otra.

La traza de una partida contra los agresivos da una pista. En el turno 61: 

[MSPACMAN] t=61  {comestible=150.0 peligro=69.0 ppill=25.0}
           → {comer=8.1 huir=1.5 irAPPill=8.4 perseguir=0.0} → gana irAPPill.
           Reglas: R2:0.56 R4:0.04 R5:0.56 R7:0.44

Con el fantasma a 69 pasos, lejos vale 0,56 y NOT lejos, 0,44. La regla 7 se activa casi a medias y le gana a comer por tres décimas: Ms. Pac-Man va a gastar la píldora con el fantasma a casi 70 pasos. Contra fantasmas que persiguen, eso es una píldora perdida. NOT lejos no significa "cerca": significa "cualquier cosa que no sea del todo lejos".

Así que la versión buena es la de seis reglas. Al concurso va mspacman-v0.fcl, que es la que carga MsPacMan(), y la v1 se queda en el proyecto para que veáis una regla que no sirve tal como está. Cambiar NOT lejos por cerca sería la v2.

De cuatro pasos, uno subió mucho, otro poco, y el último no se sostiene. Lo que más se nota no es lo más borroso: es una regla que añade una acción nueva. Las curvas suaves del paso 2 ayudan, pero poco.

05

El controlador

public class MsPacMan extends PacmanController {

    // Una ruta del disco, no del classpath: Eclipse copia el .fcl a bin/ y lanza desde la carpeta del proyecto
    static final String FCL_PATH = "bin/es/ucm/fdi/ici/c2627/practica4/grupoYY/";

    private final FuzzyEngine motor;

    public MsPacMan() {
        this("mspacman-v0.fcl");                 // la versión que va al concurso
    }

    /** Cada versión, un .fcl distinto, con el mismo Input y las mismas acciones. */
    public MsPacMan(String ficheroFcl) {
        setName("MsPacMan YY");
        setTeam("Grupo YY");
        Action[] acciones = { new ComerAction(), new HuirAction(), new IrAPPillAction(), new PerseguirAction() };
        motor = new FuzzyEngine("MSPACMAN", FCL_PATH + ficheroFcl, "MsPacMan", new MaxActionSelector(acciones));
    }

    /** Para engancharle un observador desde fuera. */
    public FuzzyEngine getMotor() { return motor; }

    @Override
    public MOVE getMove(Game game, long timeDue) {
        return motor.run(new MsPacManInput(game).getFuzzyValues(), game);
    }
}
  • El tercer argumento del FuzzyEngine es el nombre del FUNCTION_BLOCK, no el del fichero. Todos los .fcl de Ms. Pac-Man se llaman por dentro MsPacMan, así que cambiar de versión es cambiar sólo el fichero.
  • Cada versión es un .fcl, y el constructor sin argumentos apunta a la que va al concurso. El otro sirve para que Comparar juegue cualquiera de ellas sin duplicar clases.
  • El FuzzyEngine se crea en el constructor, una vez. Carga el FCL y lo reutiliza en todos los turnos: no hay reset, como en Jess, sólo valores nuevos en las entradas.
  • El orden del array de acciones decide los empates, como se vio en la sección 3.

Cómo organizar las versiones

es/ucm/fdi/ici/c2627/practica4/grupoYY/
├── MsPacMan.java          // MsPacMan() → "mspacman-v2.fcl", la del concurso
├── mspacman-v0.fcl
├── mspacman-v1.fcl
├── mspacman-v2.fcl
├── Ghosts.java            // Ghosts() → "ghosts-v1.fcl"
├── ghosts-v0.fcl
├── ghosts-v1.fcl
├── MaxActionSelector.java
├── mspacman/  MsPacManInput.java  actions/
└── ghosts/    GhostsInput.java    actions/

Si una versión necesita una entrada nueva, el Input la manda en todos los turnos y a todas las versiones, así que tiene que estar declarada en el VAR_INPUT de los .fcl anteriores, con algún término. Si no, jFuzzyLogic falla con No such variable en cada turno. Declararla sin usarla no cambia lo que hacían: por eso la v0 del ejemplo ya tiene ppill, aunque ninguna de sus reglas la mira. Si necesita una acción nueva, se añade al array y su salida sólo existe en los .fcl nuevos. Lo que no vale es cambiar una entrada o una acción que ya usaban las versiones anteriores, porque entonces sus medidas dejan de ser suyas.

06

Seguir con Ms. Pac-Man

Seis reglas que funcionan, y una que no: este controlador es sólo un punto de partida. Si lo veis jugar un rato con VerPartida, sus fallos saltan a la vista:

Lo que hace malPor quéPor dónde atacarlo
Huye mucho: en una partida contra los agresivos, en 466 de 922 turnos. Mientras huye no come, y con el fantasma a menos de 35 pasos siempre huye. Una entrada que diga si el fantasma viene hacia ella o se aleja, y reglas que sólo huyan del que se acerca.
Huye hacia otro fantasma, o hacia un callejón. HuirAction sólo mira el fantasma más cercano. Más inteligencia en la acción, como en la Práctica 1, o una entrada con el segundo fantasma más cercano.
Persigue a un comestible que se está acabando. Las reglas no saben cuánto le queda. Una entrada con el tiempo de comestible que le queda, y una regla que sólo persiga si sobra tiempo para llegar.
Gasta las píldoras de poder antes de tiempo (la v1). NOT lejos es demasiado ancho. La v2 del paso 4, y una entrada con cuántos fantasmas hay cerca: vale más con tres que con uno.
Come hacia un fantasma que viene de frente. comer va a la píldora más cercana, esté donde esté. La salida como parámetro: en vez de elegir acción, que lo borroso decida cuánto alejarse al comer, como en los apuntes.

Cómo crecer sin perder el control

  • Primero la entrada, después las reglas. Como con Jess, la mayoría de las reglas buenas salen de una entrada bien calculada en Java. Si una regla necesita cuatro AND, seguramente falta una variable.
  • Cada salida, por toda su escala. Si una salida sólo tiene reglas para mucho, se comporta como un umbral. Reglas para poco, algo y mucho hacen que su valor diga algo.
  • Para que una acción le gane a otra, que la regla baje la otra. Es la forma de ordenar prioridades sin empates, como en los pasos 3 y 4.
  • Paréntesis siempre que mezcléis AND y OR. jFuzzyLogic lee de izquierda a derecha, sin precedencia.
  • Cada regla nueva, con su caso. Una línea en ProbarBorroso con la situación para la que la escribís y la acción que debería ganar. Y su curva, para ver que no abre un hueco.
  • Y cada versión, medida. Un cambio por versión, contra los mismos rivales. Ya habéis visto que la regla de la píldora parecía buena.
Qué hace que una base borrosa sea más rica

No el número de reglas: cuatro reglas casi iguales, una por fantasma, valen lo que una. Lo que aprovecha la lógica borrosa, y lo que más se nota al leer el FCL, es lo que ha ido apareciendo en esta página: términos pensados para lo que significan, salidas que recorren su escala, reglas que combinan varias entradas, una regla que da valor a dos salidas para ordenar prioridades, y curvas de control sin huecos ni empates.

07

Seguir con los fantasmas

Cada fantasma decide por su cuenta, así que cada uno tiene su FuzzyEngine. Los cuatro cargan el mismo .fcl, pero cada motor tiene su propia copia, con sus valores y sus acciones: 

public Ghosts(String ficheroFcl) {
    setName("Ghosts YY");
    setTeam("Grupo YY");
    for (GHOST g : GHOST.values()) {
        Action[] acciones = { new PerseguirAction(g), new HuirAction(g) };
        motores.put(g, new FuzzyEngine(g.name(), MsPacMan.FCL_PATH + ficheroFcl, "Ghost",
                new MaxActionSelector(acciones)));
    }
}

@Override
public EnumMap<GHOST, MOVE> getMove(Game game, long timeDue) {
    EnumMap<GHOST, MOVE> movimientos = new EnumMap<>(GHOST.class);
    for (GHOST g : GHOST.values()) {
        if (!game.doesGhostRequireAction(g)) continue;       // fuera de los cruces no hay nada que decidir
        movimientos.put(g, motores.get(g).run(new GhostsInput(game, g).getFuzzyValues(), game));
    }
    return movimientos;
}

El Input es de cada fantasma: tres números vistos desde él.

VariableQué mide
pacmanDe mí a Ms. Pac-Man, en pasos. 150 si estoy en la cárcel.
ppillDe Ms. Pac-Man a su píldora de poder más cercana.
comestibleLos turnos que me quedan de comestible; 0 si no lo soy.
Un Input que necesita saber quién es

GhostsInput recibe el fantasma en el constructor, pero el constructor de FuzzyInput llama a parseInput() antes de que yo tenga valor. Por eso parseInput empieza con if (yo == null) return;, y el constructor de GhostsInput lo vuelve a llamar después de guardar yo. Si vuestro Input necesita algo más que el Game, os va a pasar lo mismo.

Las reglas, en ghosts-v1.fcl. La v0 es lo mismo sin la regla 3:

FUZZIFY comestible
   TERM no := (0, 1) (1, 0);
   TERM si := (0, 0) (1, 1) (200, 1);
END_FUZZIFY

RULE 1 : IF comestible IS si THEN huir IS mucho;
RULE 2 : IF comestible IS no THEN perseguir IS mucho;
// si estoy cerca de ella y ella de su píldora de poder, mejor apartarse
RULE 3 : IF comestible IS no AND pacman IS cerca AND ppill IS cerca THEN huir IS mucho, perseguir IS poco;

comestible es un número, pero sus dos términos lo convierten en un sí o un no: a partir de un turno es si del todo. Una variable nítida dentro de un sistema borroso es perfectamente normal.

Al medirlas, con Comparar en modo fantasmas, la regla 3 sale peor: 305 puntos más concedidos de media, con un umbral de 286, y repitiendo, 530 con un umbral de 288. Pero los rivales no dicen lo mismo. Contra Basico y Avanzado, la v1 concede menos puntos y le comen menos fantasmas. Contra Intermedio, le comen 5,5 fantasmas por partida en vez de 1,7, y concede 3 076 puntos más. Por qué le pasa justo con ese rival, no lo sabemos todavía: es lo que se mira con la traza, con VerPartida contra él. Mientras tanto, al concurso iría la v0, que es la que carga Ghosts().

Ideas para seguir

IdeaQué hace falta
Que no persigan los cuatro igual: si otro fantasma está más cerca de ella que yo, cortarle el paso.Una entrada con mi puesto entre los cuatro (el más cercano, el segundo…) o con la diferencia con el más cercano, y una acción cortar.
Huir con más o menos prisa según el tiempo de comestible que quede.Más términos en comestible (poco, mucho), y que huir recorra su escala.
Tapar la píldora de poder a la que va Ms. Pac-Man.Una entrada con quién llega antes a esa píldora, ella o yo, y una acción que vaya a ella.
Personalidades: Blinky persigue siempre, Sue se aparta antes.Un .fcl por fantasma. Pueden ser casi iguales y cambiar sólo los términos, o el peso de algunas reglas con WITH.
Una salida como parámetro: cuánto adelantarse a Ms. Pac-Man al perseguirla.Una salida adelanto de 0 a 20 que la acción usa para apuntar a un nodo por delante de ella.
