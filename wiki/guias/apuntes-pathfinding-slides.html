El problema

Cientos de miles de triángulos, y ninguno le sirve al personaje para decidir por dónde ir.

Parte 1 · 5

Son dos problemas, no uno

  1. Representar el espacio: convertir el mundo continuo en un grafo finito: dónde se puede estar y qué está conectado con qué.
  2. Buscar en el grafo: encontrar una secuencia de pasos de la salida al destino.

Se separan porque el algoritmo no depende de la representación. Cambiar de rejilla a malla no obliga a reescribir A*.

Parte 1 · 6

Puntos de ruta

  • Puntos interconectados, a mano o sacados de las esquinas convexas: las que sobresalen al suelo libre, por donde una ruta dobla.
  • Una arista significa: «de aquí se llega hasta ahí».
  • El NPC va al punto más cercano a su origen y busca hasta el más cercano al destino.
Parte 1 · 7

Waypoints: el balance

  • Sistema muy sencillo: no almacena información del terreno ni delimita zonas transitables.
  • Muy usado para rutas prefijadas, como las patrullas.
  • Se adapta bien a interiores con pasillos, funciona en 3D y soporta cualquier movimiento.
  • Y el defecto: rutas poco naturales… como por raíles.
Parte 1 · 8

Rejillas

  • El mapa es un array bidimensional; la posición, dos enteros.
  • Cada casilla lleva tipo de terreno y transitabilidad.
  • El NPC tiene posición real con decimales, que se trunca.
  • Necesita homogeneidad: no ve nada más fino que la casilla.
Parte 1 · 9

La misma idea, en 3D

También las hay hexagonales. La idea es la misma: casillas iguales, coordenadas enteras.

Parte 1 · 10

Malla de navegación

  • El suelo, cubierto de polígonos llamados sectores.
  • Se construyen solos desde la geometría, con una triangulación de Delaunay restringida.
  • Los sectores son convexos: dentro de uno puedo ir en línea recta.
  • Se conectan por sus aristas, los portales.

Y en Ms. Pac-Man: ya está

  • El laberinto ya es un grafo: 1293 nodos, grado máximo 4.
  • Un cruce es un nodo con tres vecinos o más. En el primer laberinto hay 38.

Parte 2 · 14

Exploración de espacios de estados

  • Estado: cada configuración posible del problema.
  • Transición: los estados a los que se llega en un paso. También, sucesores.
  • Coste: lo que cuesta una transición. Aquí, siempre 1.
  • Camino solución: del estado inicial al objetivo. Camino parcial: hasta donde vas.

Buscar un camino en un laberinto y resolver un puzle son el mismo problema.

Parte 2 · 15

Un camino solución

Eso no es el espacio de estados: es un camino dentro de él. El espacio entero son 181 440 configuraciones. En el laberinto, 1293 nodos.

Parte 2 · 16

El mapa, reducido a grafo

Las aristas pueden tener coste. En Ms. Pac-Man todas cuestan lo mismo: un turno.

Parte 2 · 17

Todos los algoritmos son el mismo bucle

function buscar(inicio, objetivo)
    frontera ← {inicio};   visitados ← ∅   // abiertos y cerrados
    while frontera no esté vacía do
        n ← sacar(frontera)               // ← AQUÍ está la diferencia
        if n = objetivo then return reconstruir(padre, n) end if
        añadir n a visitados
        for each v in sucesores(n) do
            if v ∉ visitados AND v ∉ frontera then
                padre[v] ← n;  añadir v a frontera
            end if
        end for
    end while
end function

Cola FIFO → anchura. Pila → profundidad. Prioridad → A*.

Parte 2 · 18

Abiertos y cerrados

  • Nodos abiertos: el último nodo, de momento, de un posible camino. Cada uno guarda un puntero a su padre, y por eso se puede reconstruir el camino entero.
  • Nodos cerrados: los ya expandidos; los nodos intermedios de algún camino.

Las dos listas están para gestionar la repetición de estados. ¿Y si llego al mismo estado por otro camino? Quedarse con el mejor.

Con todos los costes iguales, el primer camino que encuentra es el más corto.

Parte 2 · 21

Anchura, en pseudocódigo

function anchura(inicio, objetivo)
    cola ← cola FIFO con {inicio}
    visitados ← {inicio}
    while cola no esté vacía do
        n ← desencolar(cola)
        if n = objetivo then return reconstruir(padre, n) end if
        for each v in sucesores(n) do
            if v ∉ visitados then
                padre[v] ← n;  añadir v a visitados;  encolar(cola, v)
            end if
        end for
    end while
end function

Una pasada: cuál me pilla más cerca, y por dónde se va.

Parte 2 · 22

Primero en profundidad

Poquísima memoria y soluciones rápidas, pero no las más cortas. Sin control de visitados, además, se pierde en los ciclos.

Parte 2 · 23

Coste uniforme, o Dijkstra

  • Cola de prioridad ordenada por g(n), el coste real acumulado. Es Dijkstra.
  • Cambiar el contenedor no basta: se marca al sacar, y un nodo de la frontera puede mejorar.
  • Con costes a 1, la cola de prioridad es una FIFO y sale la anchura.

A* con h = 0 es Dijkstra. Dijkstra con costes iguales es la anchura. Los tres son el mismo bucle con otra cosa dentro de la frontera.

Parte 3 · 24

Parte 3

Heurísticas y A*

Parte 3 · 25

Heurística

Una función que devuelve un valor menor cuanto más cerca está un estado del objetivo.

  • Los tres caminos escalonados miden lo mismo: distancia Manhattan.
  • La diagonal verde es la euclídea: siempre menor o igual.
  • Y ninguna es el camino que se recorre si hay paredes.
Parte 3 · 26

Admisible y consistente

  • Admisible: nunca sobreestima. h(n) ≤ h*(n). Una heurística optimista no descarta el camino bueno; una pesimista sí.
  • Consistente o monótona: h(n) ≤ c(n, n′) + h(n′). La desigualdad triangular. Garantiza que un nodo cerrado ya tiene su mejor camino.

Con paredes por medio, Manhattan y euclídea siguen siendo admisibles, porque el camino real sólo puede ser más largo, pero se vuelven malas, y la búsqueda explora de más.

Parte 3 · 27

Las tres métricas del motor

/**
 * DM stands for Distance Metric [...]
 * PATH: the actual path distance (i.e., number of step required to reach target)
 * EUCLID: Euclidean distance using the nodes' x and y coordinates
 * MANHATTAN: Manhattan distance (absolute distance between x and y coordinates)
 */
public enum DM {
    PATH, EUCLID, MANHATTAN
}

EUCLID y MANHATTAN atraviesan las paredes. Usa siempre DM.PATH: cuenta pasos de verdad y está precalculada.

Parte 3 · 28

A*: f(n) = g(n) + h′(n)

  • g(n): coste real del camino recorrido hasta ese nodo.
  • h′(n): estimación de lo que queda hasta el final.
Si…A* esY entonces
h = 0Coste uniformeÓptimo, pero explora muchísimo más.
g = 0VorazRápido y ya no óptimo.
h = coste realEl camino, directoNi un nodo de más. El límite teórico.

g tiende a anchura, h′ tiende a profundidad. Sumados, una búsqueda que cambia de camino cuando aparece algo mejor.

Parte 3 · 29

A*, en pseudocódigo

function aEstrella(inicio, objetivo)
    abiertos ← cola de prioridad por f;   cerrados ← ∅;   g[inicio] ← 0
    while abiertos no esté vacía do
        n ← el de f menor
        if n = objetivo then return reconstruir(padre, n) end if
        mover n de abiertos a cerrados
        for each v in sucesores(n) do
            if v ∈ cerrados then continue end if
            gNuevo ← g[n] + coste(n, v)
            if v ∉ abiertos OR gNuevo < g[v] then
                padre[v] ← n;  g[v] ← gNuevo;  f[v] ← gNuevo + h(v, objetivo)
                insertar o reordenar v en abiertos
            end if
        end for
    end while
end function

Parte 4 · 32

A* está precalculado

El laberinto no cambia: al cargarlo se computan todas las distancias entre todos los pares y se guardan en media tabla, porque d(a,b) = d(b,a). Consultarlas es leer un array.

public int getShortestPathDistance(int fromNodeIndex, int toNodeIndex) {
    if (fromNodeIndex == toNodeIndex) {
        return 0;
    } else if (fromNodeIndex < toNodeIndex) {
        return currentMaze.shortestPathDistances[((toNodeIndex * (toNodeIndex + 1)) / 2) + fromNodeIndex];
    } else {
        return currentMaze.shortestPathDistances[((fromNodeIndex * (fromNodeIndex + 1)) / 2) + toNodeIndex];
    }
}
Parte 4 · 33

Cuidado: asume que puedes darte la vuelta

Es la distancia óptima en el grafo, pero ni Ms. Pac-Man ni los fantasmas pueden invertir el sentido. La tabla dirá «a tres pasos» cuando hay que dar la vuelta a la manzana. 

// Sin lastMoveMade: lectura de tabla. Óptima, pero no exacta para el juego.
int[] camino = game.getShortestPath(desde, hasta);
// Con lastMoveMade: ejecuta A* de verdad, respetando el no-retroceso.
int[] camino = game.getShortestPath(desde, hasta, ultimoMovimiento);
int    pasos  = game.getShortestPathDistance(desde, hasta, ultimoMovimiento);

Para los fantasmas, siempre la segunda.

getNextMoveTowardsTarget es voraz

// pacman.game.Game. Toda la implementación cabe aquí
public MOVE getNextMoveTowardsTarget(int from, int to, DM dm) {
    MOVE move = null;
    double minDistance = Integer.MAX_VALUE;
    for (Entry<MOVE, Integer> entry : currentMaze.graph[from].neighbourhood.entrySet()) {
        double distance = getDistance(entry.getValue(), to, dm);
        if (distance < minDistance) { minDistance = distance;  move = entry.getKey(); }
    }
    return move;
}

Mira los vecinos, se queda con el mejor, y ya. Un solo paso: sin búsqueda, sin plan, sin memoria.

Parte 5

Estrategias algorítmicas

Parte 5 · 38

Por qué «huir del más cercano» falla

Maximizar la distancia paso a paso no es estar a salvo. La corrección no es cambiar la métrica: es mirar más lejos de un paso.

Parte 5 · 39

Decidir sólo en los cruces

  • En un pasillo no hay decisión: sólo se puede seguir.
  • Devolver null hace que el motor mantenga la dirección.
  • Se acaban las oscilaciones, y sobra presupuesto para buscar de verdad en los 38 sitios que importan.
if (!game.isJunction(game.getPacmanCurrentNodeIndex())) return null;

Y el grafo sobre el que conviene razonar deja de ser el de 1293 nodos: es el de cruces y tramos.

Parte 5 · 40

Recorrer un tramo, anotando

function siguienteCruce(nodo, dirección)
    pasos ← 0
    repeat
        dirección ← la única salida de nodo que no sea volver atrás
        nodo ← vecino de nodo en dirección
        pasos ← pasos + 1
        anotar lo que haya: píldora, píldora de poder, fantasma
    until esCruce(nodo)
    return {nodo, dirección, pasos, lo anotado}
end function

Con isJunction, getPossibleMoves, getNeighbour y getMoveToMakeToReachDirectNeighbour.

Parte 5 · 42

Y en código

private boolean llegoAntes(Game game, int cruce, int misPasos) {
    for (GHOST f : GHOST.values()) {
        if (game.isGhostEdible(f))       continue;   // comestible: no es amenaza
        if (game.getGhostLairTime(f) > 0) continue;   // encerrado: no está en el mapa
        int  nodo = game.getGhostCurrentNodeIndex(f);
        MOVE ult  = game.getGhostLastMoveMade(f);
        int  susPasos = game.getShortestPathDistance(nodo, cruce, ult);
        if (susPasos < misPasos + HOLGURA) return false;
    }
    return true;
}

Sin las dos exclusiones huyes de puntos gratis. Y la HOLGURA está porque empatar es perder.

Parte 5 · 43

Dos cruces por delante

function movimientosSeguros()
    árbol ← mapa vacío
    for each d in salidasLegales(miNodo, miÚltimoMov) do
        c1 ← siguienteCruce(miNodo, d)
        if hayFantasmaEnElTramo(c1) OR NOT llegoAntes(c1.nodo, c1.pasos) then continue end if
        árbol[d] ← ∅
        for each d2 in salidasLegales(c1.nodo, c1.dirección) do
            c2 ← siguienteCruce(c1.nodo, d2)
            if llegoAntes(c2.nodo, c1.pasos + c2.pasos) then añadir d2 a árbol[d] end if
        end for
    end for
    return árbol
end function

Conjunto vacío = trampa, aunque el primer tramo sea seguro.

Parte 5 · 44

Anchura, restringida a lo seguro

function buscarObjetivoSeguro(objetivos, árbol)
    cola ← cola FIFO;   visitados ← {miNodo}
    for each d in claves de árbol do   // sólo arranco por lo seguro
        v ← vecino de miNodo en d;  padre[v] ← miNodo;  añadir v a visitados;  encolar(cola, {v, d})
    end for
    while cola no esté vacía do
        {n, dir} ← desencolar(cola);   if n ∈ objetivos then return primer paso de reconstruir(padre, n) end if
        for each v in salidasLegales(n, dir) do
            if v ∉ visitados then padre[v] ← n;  añadir v a visitados;  encolar(cola, {v, dir. de n a v}) end if
        end for
    end while
end function

getClosestNodeIndexFromNodeIndex hace lo mismo, pero no ve los fantasmas.

Tema 1 · 50

Lo que hay que llevarse

  1. El pathfinding son dos problemas: representar y buscar.
  2. Todo algoritmo de búsqueda es el mismo bucle sobre abiertos y cerrados.
  3. Anchura con costes unitarios ya es óptima. En el laberinto, es la herramienta.
  4. Heurística admisible ⇒ A* óptimo.
  5. DM.PATH siempre: las otras dos atraviesan paredes.
  6. El camino te lo da el motor. La decisión no, y ahí está la nota.
