Tema 3 · 06 · Sistemas de reglas

Reglas en Ms. Pac-Man El paquete rules del motor, un turno por dentro y cómo darle memoria a un sistema que no la tiene.

Lo que pasa en un turno, de getMove al movimiento: los hechos que escribe el Input, las reglas del .clp, el ACTION que gana y la acción Java que lo ejecuta. Después, la plantilla de la práctica leída línea a línea, la forma de recordar cosas entre turnos y los errores que os vais a encontrar.

Si habéis hecho la Práctica 2, la mitad de esto ya os suena: el motor de reglas reutiliza la misma idea de Input y de Action que el paquete fsm. Lo que cambia es quién decide. En la máquina de estados, las transiciones que añadíais con FSM.add; aquí, unas reglas escritas en un fichero aparte, fuera del código Java, que Jess lee al arrancar.

Para la Práctica 3

Esta página explica las piezas. Montadas en un controlador entero, con siete reglas añadidas de una en una y medidas, están en Ms. Pac-Man con siete reglas, con su proyecto para descargar. Y para ver qué reglas se disparan mientras se juega, más allá del observador de la sección 6, en Depurar reglas.

01

Un turno, de principio a fin

Un detalle importante del paso 2: en cada turno se vacía la memoria. Los hechos del turno anterior desaparecen, y las reglas razonan sólo con lo que el Input diga ahora. Como en un árbol de comportamiento sin pizarra, el sistema no se acuerda de nada. Volveremos a esto en la sección 5, porque es lo que separa un fantasma de reglas de uno de estados.

02

RulesInput: el juego, como hechos

Es un Input como el de la Práctica 2 (el constructor llama a parseInput(), que lee el Game una vez) con un método más, getFacts(), que devuelve los hechos del turno como cadenas en sintaxis CLIPS. Así es el de la plantilla: 

public class GhostsInput extends RulesInput {

    private boolean BLINKYedible, INKYedible, PINKYedible, SUEedible;
    private double minPacmanDistancePPill;

    public GhostsInput(Game game) { super(game); }

    @Override
    public void parseInput() {
        BLINKYedible = game.isGhostEdible(GHOST.BLINKY);
        // … lo mismo para INKY, PINKY y SUE …
        int pacman = game.getPacmanCurrentNodeIndex();
        minPacmanDistancePPill = Double.MAX_VALUE;
        for (int ppill : game.getPowerPillIndices())
            minPacmanDistancePPill = Math.min(minPacmanDistancePPill,
                    game.getDistance(pacman, ppill, DM.PATH));
    }

    @Override
    public Collection<String> getFacts() {
        Vector<String> facts = new Vector<>();
        facts.add(String.format("(BLINKY (edible %s))", BLINKYedible));
        // … INKY, PINKY, SUE …
        facts.add(String.format("(MSPACMAN (mindistancePPill %d))", (int) minPacmanDistancePPill));
        return facts;
    }
}

Cada cadena tiene que corresponder a una plantilla declarada en el .clp, con los mismos nombres de slot. Java no lo comprueba al compilar: si escribís edibel en un sitio y edible en el otro, os enteráis en la consola cuando ya está la partida en marcha.

Qué meter en los hechos

Lo mismo que en la Práctica 2: lo que se mide, no lo que se decide. Distancias, tiempos, "¿llego yo antes?", "¿cuántos fantasmas hay cerca?". Si una pregunta necesita caminos o bucles, calculadla aquí en Java, que es donde se calcula bien, y pasadle a Jess el resultado. Lo que hacer con esas medidas es lo que va en las reglas.

03

El fichero .clp: plantillas, reglas y ACTION

Hay un fichero de reglas por fantasma (blinkyrules.clp, inkyrules.clp…), en el mismo paquete que las clases. Cada uno empieza declarando las plantillas de los hechos que aserta el Input, y después la del hecho de salida, ACTION: 

; los hechos que aserta GhostsInput
(deftemplate BLINKY (slot edible (type SYMBOL)))
(deftemplate INKY   (slot edible (type SYMBOL)))
(deftemplate PINKY  (slot edible (type SYMBOL)))
(deftemplate SUE    (slot edible (type SYMBOL)))
(deftemplate MSPACMAN (slot mindistancePPill (type NUMBER)))

; el hecho de salida: id y priority son obligatorios
(deftemplate ACTION
   (slot id) (slot info (default "")) (slot priority (type NUMBER))
   (slot runawaystrategy (type SYMBOL)))       ; un slot extra, para RunAwayAction

(defrule BLINKYrunsAwayMSPACMANclosePPill
   (MSPACMAN (mindistancePPill ?d)) (test (<= ?d 30))
   =>
   (assert (ACTION (id BLINKYrunsAway) (info "MSPacMan cerca PPill") (priority 50)
                   (runawaystrategy RANDOM))))

(defrule BLINKYrunsAway
   (BLINKY (edible true))
   =>
   (assert (ACTION (id BLINKYrunsAway) (info "Comestible --> huir") (priority 30)
                   (runawaystrategy CORNER))))

(defrule BLINKYchases
   (BLINKY (edible false))
   =>
   (assert (ACTION (id BLINKYchases) (info "No comestible --> perseguir") (priority 10))))

Los slots de ACTION tienen tres papeles:

  • id dice qué acción Java ejecutar: es la clave del mapa de acciones.
  • priority decide cuál gana cuando se asertan varios. Recordad que no es la salience: se disparan todas las reglas, y la elección es posterior.
  • info y cualquier slot que añadáis (aquí runawaystrategy) son parámetros: la acción los lee con parseFact. Así una sola clase RunAwayAction puede huir de varias formas, y es la regla la que dice de cuál.

Fijaos en que BLINKYrunsAway se aserta desde dos reglas con dos prioridades y dos estrategias distintas. Es normal y es útil: "huir" es una acción, pero hay varias razones para huir, cada una con su urgencia.

04

RuleEngine y RulesAction: el lado de Java

Una acción es una clase que implementa RulesAction: la execute(Game) de siempre, un getActionId() y un método nuevo, parseFact, que recibe el hecho ACTION ganador para leer sus parámetros: 

public class RunAwayAction implements RulesAction {
    enum STRATEGY { RANDOM, CORNER, JAIL }
    GHOST ghost;
    STRATEGY runAwayStrategy;

    public RunAwayAction(GHOST ghost) { this.ghost = ghost; }

    @Override
    public void parseFact(Fact actionFact) {
        try {
            Value value = actionFact.getSlotValue("runawaystrategy");
            if (value == null) return;
            runAwayStrategy = STRATEGY.valueOf(value.stringValue(null));
        } catch (JessException e) { e.printStackTrace(); }
    }

    @Override
    public MOVE execute(Game game) {
        // aquí runAwayStrategy dice cómo huir
        if (!game.doesGhostRequireAction(ghost)) return MOVE.NEUTRAL;
        return game.getApproximateNextMoveAwayFromTarget(game.getGhostCurrentNodeIndex(ghost),
                game.getPacmanCurrentNodeIndex(), game.getGhostLastMoveMade(ghost), DM.PATH);
    }

    @Override
    public String getActionId() { return ghost + "runsAway"; }
}

Y el controlador lo junta todo: un mapa de acciones por id, y un motor por fantasma, cada uno con su fichero de reglas. 

public Ghosts() {
    map = new HashMap<>();
    map.put("BLINKYchases", new ChaseAction(GHOST.BLINKY));
    map.put("BLINKYrunsAway", new RunAwayAction(GHOST.BLINKY));
    // … las de INKY, PINKY y SUE …

    ghostRuleEngines = new EnumMap<>(GHOST.class);
    for (GHOST ghost : GHOST.values()) {
        String rulesFile = String.format("%s%srules.clp", RULES_PATH, ghost.name().toLowerCase());
        ghostRuleEngines.put(ghost, new RuleEngine(ghost.name(), rulesFile, map));
    }
}

@Override
public EnumMap<GHOST, MOVE> getMove(Game game, long timeDue) {
    RulesInput input = new GhostsInput(game);          // paso 1, una vez para los cuatro
    EnumMap<GHOST, MOVE> result = new EnumMap<>(GHOST.class);
    for (GHOST ghost : GHOST.values()) {
        RuleEngine engine = ghostRuleEngines.get(ghost);
        engine.reset();                                    // paso 2
        engine.assertFacts(input.getFacts());              // paso 3
        result.put(ghost, engine.run(game));               // pasos 4 a 6
    }
    return result;
}

Los cuatro motores comparten el Input (ven los mismos hechos) y el mapa, pero cada uno tiene sus reglas. La ruta del fichero, RULES_PATH, es la del paquete escrita con barras: Eclipse copia el .clp a bin al compilar y Jess lo busca en el classpath. Si cambiáis el nombre del paquete, cambiad también esa constante.

Y esto es todo lo que hace RuleEngine.run después del jess.run(), resumido: 

// de todos los hechos de la memoria, los ACTION, y de ellos el de priority más alta
Fact action = null;
int max = Integer.MIN_VALUE;
for (Fact f : todosLosHechos)
    if (f.getName().startsWith("MAIN::ACTION") && f.getSlotValue("priority").intValue(null) > max) {
        action = f;
        max = f.getSlotValue("priority").intValue(null);
    }
RulesAction a = map.get(action.getSlotValue("id").toString());
a.parseFact(action);
return a.execute(game);              // y si algo falla por el camino: MOVE.NEUTRAL

Es un > estricto: con dos ACTION de la misma prioridad gana el primero de la lista, el que se asertó antes. Y si no se aserta ningún ACTION, o salta cualquier excepción, el fantasma devuelve MOVE.NEUTRAL y sigue recto, que es el síntoma de casi todos los errores de la sección 7.

05

Recordar entre turnos: histéresis con reglas

En la Práctica 2 medimos que un fantasma con un solo umbral (huir a menos de 30 de la píldora, dejar de huir a 30 o más) cambia de idea sin parar cuando Ms. Pac-Man ronda los 30. La máquina lo arreglaba con histéresis porque sabía en qué estado estaba. Las reglas de la plantilla tienen exactamente el problema de la lista de prioridades: como la memoria se vacía en cada turno, no hay forma de escribir "sigue huyendo hasta los 40".

La salida es darle a Jess lo que necesita recordar como un hecho más. La memoria vive en Java, que es lo que sobrevive entre turnos, y el Input la aserta junto con lo demás. Por ejemplo, la última acción de cada fantasma, que la puede apuntar la propia acción cuando se ejecuta: 

// una forma de hacerlo: la acción apunta que ha ganado
public MOVE execute(Game game) {
    memoria.put(ghost, "runsAway");      // un EnumMap<GHOST,String> compartido
    …
}

// y el Input la convierte en un hecho más
facts.add(String.format("(BLINKY (edible %s) (ultima %s))", BLINKYedible, memoria.get(GHOST.BLINKY)));
(deftemplate BLINKY (slot edible) (slot ultima (default nada)))

; entrar en la huida: a menos de 30
(defrule BLINKYempiezaAHuir
   (MSPACMAN (mindistancePPill ?d&:(< ?d 30)))
   =>
   (assert (ACTION (id BLINKYrunsAway) (info "entra: PPill a menos de 30") (priority 50))))

; seguir huyendo: si ya huía, hasta los 40
(defrule BLINKYsigueHuyendo
   (BLINKY (ultima runsAway))
   (MSPACMAN (mindistancePPill ?d&:(< ?d 40)))
   =>
   (assert (ACTION (id BLINKYrunsAway) (info "sigue: aún a menos de 40") (priority 50))))

Con esto, entre 30 y 40 el fantasma hace lo mismo que hizo en el turno anterior, como la máquina de estados. Pero fijaos en lo que ha costado: la memoria la habéis tenido que programar vosotros, en Java, y hacerla llegar como un hecho. En la máquina venía de serie. Es uno de los argumentos de la comparación final.

Que la memoria no se convierta en una máquina de estados escondida

Recordad lo justo para lo que necesitáis: la última acción, un contador de turnos, el último sitio donde se vio a Ms. Pac-Man. Si acabáis con un slot estado y una regla por cada pareja de estados, habéis escrito una máquina de estados en CLIPS, y para eso era mejor la de la Práctica 2.

06

Ver qué reglas se disparan mientras se juega

Como en el paquete fsm, el motor admite observadores. El de la plantilla escribe en la consola: 

ConsoleRuleEngineObserver observer = new ConsoleRuleEngineObserver(GHOST.BLINKY.name(), true);
ghostRuleEngines.get(GHOST.BLINKY).addObserver(observer);

Con true como segundo argumento, en cada turno vuelca la memoria de trabajo entera después de run (los hechos del Input y todos los ACTION asertados) y después el que ha ganado. Con false, sólo la última línea: 

***** Rules for BLINKY *****
(MAIN::initial-fact)
(MAIN::BLINKY (edible false))
(MAIN::INKY (edible false))
(MAIN::PINKY (edible true))
(MAIN::SUE (edible false))
(MAIN::MSPACMAN (mindistancePPill 25))
(MAIN::ACTION (id BLINKYrunsAway) (info "MSPacMan cerca PPill") (priority 50) (runawaystrategy RANDOM))
(MAIN::ACTION (id BLINKYchases) (info "No comestible --> perseguir") (priority 10) (runawaystrategy nil))
[BLINKY] action fired: (MAIN::ACTION (id BLINKYrunsAway) (info "MSPacMan cerca PPill") (priority 50) (runawaystrategy RANDOM))

Para eso sirve el slot info: en esa traza se lee por qué ganó cada acción. Escribidlo pensando en vosotros dentro de una semana, mirando una partida que ha salido mal. Y activad el observador sólo en el fantasma que estéis depurando: cuatro motores volcando la memoria en cada turno son cientos de líneas por segundo.

Para probar una regla concreta sin jugar, lo más rápido es la consola de Jess con unos hechos de prueba, como se cuenta en la página de CLIPS.

07

Errores típicos

Lo que pasaPor qué, y qué hacer
En la consola sale Exception assserting fact y una regla que debería dispararse no se dispara. Un hecho del Input no tiene plantilla en el .clp, o tiene un slot que la plantilla no declara. Jess no lo aserta. Comparad letra a letra la cadena de getFacts con el deftemplate, y recordad que cada fichero de reglas tiene que declarar todas las plantillas de los hechos que se le asertan, también las de los otros fantasmas.
Una regla con (edible TRUE) no se dispara nunca. String.format("%s", true) escribe true, en minúsculas, y para Jess true y TRUE son símbolos distintos. Escribid en las reglas exactamente lo que escribe Java.
El fantasma se queda recto y en la consola sale Exception executing rules. Lo más probable: el id del ACTION ganador no está en el mapa (una errata, o una acción que no habéis registrado con map.put). También pasa si a un ACTION le falta priority: queda a nil y no se puede comparar.
Sale Exception loading rules from file al arrancar y ningún fantasma decide. El .clp tiene un error de sintaxis (casi siempre un paréntesis) o la ruta no es la del paquete. Cargadlo en la consola de Jess: el mensaje dice la línea. Y si usáis allowed-symbols o range, quitadlos: Jess 7.1 no los entiende.
Un fantasma hace lo que debería hacer otro. Al copiar las reglas de Blinky para Pinky, alguna se ha quedado preguntando por BLINKY o asertando BLINKYchases. El motor de Pinky ejecuta entonces la acción de Blinky, que calcula el movimiento de Blinky, y se lo da a Pinky. Repasad cada fichero buscando el nombre de los otros tres.
A veces hace una cosa y a veces otra, sin que cambie nada. Dos ACTION con la misma priority: gana el que se asertó antes, que depende del orden de disparo. Dad prioridades distintas a las acciones que pueden coincidir.
El juego se congela en cuanto se cumple una regla. Una regla que modifica o reaserta lo mismo que la activa: el bucle de modify. Con el reset en cada turno y reglas que sólo asertan ACTION, no debería pasar; si pasa, buscad un modify o un retract.
Vuestras reglas "funcionan", pero el fantasma oscila entre perseguir y huir. No es un error de Jess: es la falta de memoria de la sección 5. Dos umbrales y la última acción como hecho.
