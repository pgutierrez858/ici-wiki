Asignatura / Guías / Tema 2 / Lógica borrosa en Ms. Pac-Man

Tema 2 · 10 · Razonamiento borroso

Lógica borrosa en Ms. Pac-Man FCL, jFuzzyLogic y el paquete fuzzy del motor, de las distancias a un movimiento.

El fichero FCL pieza a pieza, cómo probarlo desde la consola, y lo que hace el motor en cada turno: el FuzzyInput que mide, jFuzzyLogic que razona y el ActionSelector que convierte unos números en un movimiento. Con la visibilidad parcial, los errores típicos y una comparación final con las reglas de Jess.

01

El fichero FCL, pieza a pieza

FCL (Fuzzy Control Language) es un lenguaje estándar para describir sistemas borrosos, de la norma IEC 61131-7 de los autómatas industriales. jFuzzyLogic lo lee y lo ejecuta desde Java. Como el .clp de Jess, va en un fichero aparte del código, y el conocimiento queda fuera del Java. Un bloque completo, el del banco de pruebas: 

FUNCTION_BLOCK huida                // un bloque; un fichero puede tener varios

VAR_INPUT                           // lo que llega del juego
   fantasma : REAL;
   ppill    : REAL;
END_VAR

VAR_OUTPUT                          // lo que sale
   huir : REAL;
END_VAR

FUZZIFY fantasma                    // los términos de cada entrada
   TERM cerca := (0, 1) (15, 1) (45, 0);
   TERM media := trian 20 50 80;
   TERM lejos := (55, 0) (85, 1) (100, 1);
END_FUZZIFY

FUZZIFY ppill
   TERM cerca := (0, 1) (10, 1) (40, 0);
   TERM lejos := (20, 0) (60, 1) (100, 1);
END_FUZZIFY

DEFUZZIFY huir                      // los términos de la salida y cómo se desdifumina
   TERM poco  := (0, 1) (4, 0);
   TERM algo  := trian 2 5 8;
   TERM mucho := (6, 0) (10, 1);
   METHOD : COG;
   DEFAULT := 0;                    // lo que sale si no se activa ninguna regla
END_DEFUZZIFY

RULEBLOCK reglas
   AND : MIN;                       // y por tanto OR : MAX
   ACT : MIN;
   ACCU : MAX;
   RULE 1 : IF fantasma IS cerca AND ppill IS lejos THEN huir IS mucho;
   RULE 2 : IF fantasma IS cerca AND ppill IS cerca THEN huir IS poco;
   RULE 3 : IF fantasma IS media THEN huir IS algo;
   RULE 4 : IF fantasma IS lejos THEN huir IS poco;
END_RULEBLOCK

END_FUNCTION_BLOCK
Se escribeQué hace
TERM t := (x, y) (x, y) …;Término por puntos, de menor a mayor x. Fuera de los puntos se queda con el valor del extremo.
trian a b c · trape a b c d · gauss m σTriángulo, trapecio y campana. Fuera del triángulo y del trapecio vale 0.
RANGE := (0 .. 30);En un DEFUZZIFY, fija el universo de la salida. Si no, va del extremo izquierdo al derecho de sus términos (una gaussiana llega a ±4σ).
IF x IS NOT t · NOT (…)Negación: 1 − μ.
THEN a IS t1, b IS t2Una regla puede dar valor a varias salidas.
… THEN a IS t WITH 0.5;Peso de la regla: su grado se multiplica por 0,5.
En jFuzzyLogic, el AND no va antes que el OR

En casi todos los lenguajes, a OR b AND c es a OR (b AND c). En jFuzzyLogic, no: lee de izquierda a derecha y entiende (a OR b) AND c. Lo hemos comprobado con la versión del motor: con a a 1 y b y c a 0, la regla se activa con un 0, no con un 1. Siempre que mezcléis AND y OR, poned paréntesis.

02

Probar un FCL sin lanzar el juego

jFuzzyLogic.jar, que viene en MsPacManEngine/lib, se puede ejecutar solo. En Eclipse, una Run Configuration de tipo Java Application con Main class net.sourceforge.jFuzzyLogic.JFuzzyLogic, o desde una terminal: 

java -jar jFuzzyLogic.jar huida.fcl                  # dibuja los términos de cada variable
java -jar jFuzzyLogic.jar -e huida.fcl 25 50         # evalúa con esas entradas

Con -e escribe las variables, la salida y el grado con el que se ha activado cada regla, que es lo que más ayuda a depurar: 

	VAR_INPUT 	  fantasma = 25.000000
	VAR_OUTPUT	      huir = 7.372145
	VAR_INPUT 	     ppill = 50.000000
	RULE_BLOCK reglas
		Support  	Rule name 	Rule
		0.666667	1         	IF (fantasma IS cerca) AND (ppill IS lejos) THEN huir IS mucho;
		0.000000	2         	IF (fantasma IS cerca) AND (ppill IS cerca) THEN huir IS poco;
		0.166667	3         	IF fantasma IS media THEN huir IS algo;
		0.000000	4         	IF fantasma IS lejos THEN huir IS poco;
El orden de los números con -e

Los valores no se asignan en el orden en que declaráis las variables, sino en orden alfabético de sus nombres, que es también el orden en que las lista. En tipper.fcl se declara primero service y después food, pero -e tipper.fcl 8 3 da food = 8 y service = 3. Mirad siempre las líneas VAR_INPUT para comprobar qué le ha tocado a cada una.

Si el FCL tiene un error de sintaxis, jFuzzyLogic lo dice con la línea y la columna (line 15:3 missing SEMICOLON at 'TERM') y, ojo, a veces sigue adelante como si nada. Leed lo que escribe al cargar.

03

El paquete fuzzy del motor

Es la tercera vez que lo veis, con otra pieza en medio: un Input que mide, un motor que razona y unas acciones que mueven. Lo nuevo es el ActionSelector, porque el sistema borroso no devuelve una acción sino números, y alguien tiene que decidir qué hacer con ellos. 

public class MsPacManInput extends FuzzyInput {
    private double[] distance;

    public MsPacManInput(Game game) { super(game); }

    @Override
    public void parseInput() {
        distance = new double[4];
        for (GHOST g : GHOST.values()) {
            int pos = game.getGhostCurrentNodeIndex(g);      // -1 si no se ve
            distance[g.ordinal()] = pos == -1 ? -1
                    : game.getDistance(game.getPacmanCurrentNodeIndex(), pos, DM.PATH);
        }
    }

    @Override
    public HashMap<String, Double> getFuzzyValues() {
        HashMap<String, Double> vars = new HashMap<>();
        for (GHOST g : GHOST.values())
            vars.put(g.name() + "distance", distance[g.ordinal()]);   // la clave = el nombre en VAR_INPUT
        return vars;
    }
}
public MsPacMan() {
    Action[] actions = { new GoToPPillAction(), new RunAwayAction() };
    ActionSelector actionSelector = new MaxActionSelector(actions);
    fuzzyEngine = new FuzzyEngine("MsPacMan",
            RULES_PATH + "mspacman.fcl",        // ruta en el disco: "bin/es/ucm/…/mspacman/"
            "FuzzyMsPacMan",                      // el nombre del FUNCTION_BLOCK
            actionSelector);
}

@Override
public MOVE getMove(Game game, long timeDue) {
    MsPacManInput input = new MsPacManInput(game);
    return fuzzyEngine.run(input.getFuzzyValues(), game);
}

Dos diferencias con Jess. La primera, el fichero se carga con una ruta del disco, no del classpath: "bin/es/ucm/…" funciona porque Eclipse lanza el programa desde la carpeta del proyecto. La segunda, no hay reset: el mismo sistema borroso se reutiliza en cada turno, y lo que cambia son los valores de las variables.

04

De números a una acción

La plantilla trae un MaxActionSelector: hay una variable de salida por acción, con el mismo nombre que el getActionId() de la acción, y gana la que tenga el valor más alto. 

public Action selectAction(HashMap<String, Double> fuzzyOutput) {
    double max = Double.NEGATIVE_INFINITY;
    String actionName = null;
    for (Entry<String, Double> e : fuzzyOutput.entrySet())
        if (e.getValue() > max) { max = e.getValue(); actionName = e.getKey(); }
    for (Action a : actions)
        if (a.getActionId().equals(actionName)) return a;
    return null;
}

Es la forma más directa de llevar "cuánto me conviene cada cosa" a una decisión, y es la idea de la IA de utilidad. Pero sólo funciona si los números de las distintas salidas se pueden comparar, y eso hay que diseñarlo:

  • La misma escala para todas. Si Runaway va de 0 a 30 y GoToPPill de 0 a 10, compararlas no tiene sentido.
  • Términos que cubran la escala (poco, algo, mucho), para que la salida crezca de verdad con la conveniencia. Recordad la tercera trampa: con un solo término activo, el centro de gravedad casi no se mueve, y si ese término es una campana en el centro de la escala, la salida será siempre ese centro, se active la regla con un 0,1 o con un 1.
  • Un DEFAULT bajo para cada salida, para que "ninguna regla dice nada" signifique "no me conviene", no "me conviene a medias".

Hay otras formas de usar la salida, y a veces son mejores:

DiseñoCómo esCuándo conviene
Una salida por acción y gana la mayorEl MaxActionSelector de la plantilla.Pocas acciones, cada una con reglas claras de cuándo conviene.
Una sola salida, partida en tramos"Agresividad" de 0 a 10: por debajo de 3 huir, de 3 a 7 comer pastillas, por encima de 7 cazar.Cuando las acciones son grados de una misma cosa.
La salida como parámetroLa lógica borrosa no elige qué hacer, sino cuánto: cuántos pasos de margen dejar con el fantasma, o qué peso dar a cada objetivo en un mapa de influencia.Cuando la decisión ya está clara y lo vago es la intensidad.
05

Visibilidad parcial y memoria

La plantilla del curso pasado jugaba con visibilidad parcial: Ms. Pac-Man sólo ve a los fantasmas que tiene cerca, y de los demás getGhostCurrentNodeIndex devuelve −1. Es un caso perfecto para la lógica borrosa, porque aparece una magnitud vaga de verdad: cuánto me fío de lo que sé de cada fantasma. La plantilla la llama confianza: 100 si lo estoy viendo, y cinco puntos menos por cada turno que pasa sin verlo. Así las reglas pueden decir "si Blinky está cerca y la confianza es alta, emergencia".

Para que eso funcione, la memoria tiene que guardarse de un turno a otro. Esto es lo que hay que hacer con la confianza, en una clase que vive tanto como el controlador: 

double[] confidence = { 100, 100, 100, 100 };     // un campo: sobrevive entre turnos

public void update(MsPacManInput input) {
    for (GHOST g : GHOST.values()) {
        int i = g.ordinal();
        confidence[i] = input.isVisible(g) ? 100 : Math.max(0, confidence[i] - 5);   // ← guardarlo, no sólo calcularlo
        mem.put(g.name() + "confidence", confidence[i]);
    }
}
El fantasma invisible que está encima

Si a un fantasma que no se ve le pasáis −1 como distancia, recordad cómo se evalúa un término por puntos fuera de su rango: TERM near := (0, 1) (60, 0) se queda con el valor del extremo, y −1 es cerca con un 1. El fantasma que no veis cuenta como si lo tuvierais pegado. Para un fantasma que no se ve, pasad la última distancia conocida (y que la confianza haga su trabajo), o una distancia muy grande. Y no lo dejéis sin valor: una variable a la que no le dais valor en un turno se queda con el del turno anterior, sin avisar.

07

Errores típicos

Lo que pasaPor qué, y qué hacer
Al arrancar sale Can't load file, y luego Error evaluating fuzzy logic en cada turno.La ruta del .fcl no existe desde la carpeta en la que se lanza el programa. Comprobad la ruta, y probad el fichero con la consola de jFuzzyLogic.
No such variable: 'BlinkyDistance'.Una clave del mapa del Input no coincide con un nombre de VAR_INPUT. Las mayúsculas cuentan.
Un fantasma invisible hace huir a Ms. Pac-Man.La distancia −1 fuera de rango, que vale "cerca" con un 1. Ved la sección 5.
La confianza no baja nunca de 95.Se calcula la nueva confianza pero no se guarda en el campo, así que cada turno se vuelve a calcular desde 100.
Una salida vale siempre lo mismo, pase lo que pase.Sólo se activa un término, y su centro de gravedad no depende del grado. Más términos en la escala, o más reglas que la repartan.
Ms. Pac-Man se tranquiliza cuando un fantasma se aleja, aunque otro esté encima.Reglas de "calma" que deberían exigir que todos estén lejos. La primera trampa.
Con ciertas distancias, la salida cae de golpe al DEFAULT.Un hueco entre términos. Que se solapen.
Una regla con OR y AND se activa cuando no debería.La precedencia de jFuzzyLogic: de izquierda a derecha. Paréntesis.
Con METHOD : MM salen valores absurdos, cerca de 0.El error de jFuzzyLogic 3.2 con la media de los máximos. Usad COG.
08

Reglas nítidas y reglas borrosas

Jess (Práctica 3)jFuzzyLogic (Práctica 4)
Qué entraHechos, de cualquier forma: símbolos, números, relaciones.Números, uno por variable.
Qué saleUn hecho ACTION que dice qué hacer.Números, uno por variable de salida, que hay que convertir en una acción.
Varias reglas a la vezSe disparan todas, y se elige por prioridad.Se mezclan, cada una con su grado.
Razonar por capasSí: reglas que deducen hechos que usan otras.No dentro de un bloque: las salidas no alimentan otras reglas. Se puede encadenar en Java, con un bloque detrás de otro.
UmbralesBruscos: el comportamiento salta.Suaves: el comportamiento cambia poco a poco.
Se depura mirandoQué reglas se han disparado.La curva de control: qué sale para cada entrada.
Lo difícilQue las prioridades no tapen reglas mal escritas.Colocar bien los términos y que las reglas no se contradigan.

No compiten: resuelven partes distintas del problema. Las reglas de Jess son buenas para qué hacer cuando las situaciones son distintas entre sí ("si es comestible, huye"); las borrosas, para cuánto cuando la situación cambia de forma continua ("cuánta prisa tengo por huir"). Muchos sistemas reales combinan las dos, y no es raro que en vuestra Práctica 4 la mejor decisión salga de unas pocas reglas borrosas bien medidas más un par de condiciones nítidas en Java.
