Probar los controladores y la competición Cómo medir lo que hacen, cómo se juega el concurso y de dónde sale el punto extra.

Un controlador no se juzga viéndolo jugar una partida: se juzga con la media de unos cuantos cientos. Aquí está cómo montar esas pruebas, cómo se ejecuta el concurso de todos contra todos con el que se cierra cada práctica, con qué cuenta exacta sale el punto extra, y qué herramientas trae el motor para guardar métricas, depurar y ver lo que está pasando.

01

Tres formas de ejecutar, y cuándo usar cada una

El Executor tiene muchos métodos para lanzar partidas, pero en la práctica sólo se usan tres, y cada uno contesta a una pregunta distinta. Confundirlos es la causa número uno de «pero si a mí me iba bien».

Qué Para qué Ventana
runGame(pacman, ghosts, delay) Mirar. Una partida, con pausa entre turnos, para ver qué decide vuestro controlador y por qué se muere. No sirve para comparar nada. Sí
runExperiment(pacman, ghosts, n, desc) Medir. n partidas seguidas, sin dibujar, y devuelve un Stats con la media. Es el modo con el que se corrige. No
PacManParallelEvaluator Competir. Todos los controladores contra todos, en paralelo, y saca la tabla y los dos rankings. Es el modo con el que se juega el concurso. No

Los tres esperan a que vuestro getMove conteste: no hay reloj. Si tardáis 200 ms, la partida tarda 200 ms más en ese turno y vuestro movimiento se usa entero. Lo único que se paga es que la tanda entera tarde más, y en 50 000 partidas eso sí se nota. El detalle completo está en las reglas de simulación de la Práctica 1.

El banco de pruebas mínimo

Este es el main que conviene tener desde el primer día, con un interruptor para pasar de mirar a medir sin tocar nada más: 

public class ExecutorTest {

    private static final boolean VER = false;   // true: una partida mirándola
    private static final int     N   = 100;     // false: N partidas midiendo

    public static void main(String[] args) {
        PacmanController pacMan = new MsPacMan();
        GhostController  ghosts = new Ghosts();

        Executor executor = new Executor.Builder()
                .setTickLimit(4000)
                .setPacmanPO(false)
                .setGhostPO(false)
                .setGhostsMessage(false)
                .setVisual(VER)
                .setScaleFactor(2.5)
                .build();

        if (VER) {
            executor.runGame(pacMan, ghosts, 40);
        } else {
            Stats[] stats = executor.runExperiment(pacMan, ghosts, N, "nuestros contra nuestros");
            System.out.println(stats[0]);   // puntuación
            System.out.println(stats[1]);   // turnos por partida
        }
    }
}
Los dos Stats que devuelve

runExperiment devuelve un array de dos: el primero es la puntuación y el segundo los turnos que duró cada partida. El segundo se ignora siempre y es una pena, porque cuenta cosas que la puntuación esconde: una Ms. Pac-Man que puntúa poco y dura poco se está muriendo; una que puntúa poco y dura 4000 turnos está viva y no come, que es un problema completamente distinto.

02

Medir: la media y el error típico

Una partida no dice nada. Dos controladores idénticos pueden separarse 3 000 puntos en una partida suelta, porque el motor arranca cada partida con una semilla distinta y porque una píldora de poder bien gastada vale 3 000 puntos ella sola. Lo que se compara es la media, y la media viene con su propio margen de error.

Método de StatsQué es
getAverage()La media de todas las partidas. Es el número con el que se ordenan los rankings del concurso.
getStandardDeviation()Cuánto se separan unas partidas de otras. Es lo irregular que es vuestro controlador, así que jugar más partidas no la baja: no mide el experimento, os mide a vosotros.
getStandardError()Lo mismo pero un piso más arriba: cuánto se separarían unas medias de otras si repitierais el experimento entero. Sale de dividir la anterior por la raíz de las partidas jugadas, y es el número que decide si una mejora es real. Explicado justo debajo.
getN()Partidas que han contado de verdad. Si salen menos de las que pedisteis, ha habido excepciones.
getMin() · getMax()La peor y la mejor de todas las partidas. La peor dice más: si es 0, hay partidas en las que Ms. Pac-Man muere sin comerse una sola píldora.
getMsTaken()Lo que ha tardado el experimento entero, en milisegundos. Dividido entre las partidas da lo que cuesta una, que es lo que hay que saber antes de planificar: no lo estiméis a ojo, porque depende muchísimo de lo que haga vuestro controlador y de cuánto sobreviva. Como referencia, el concurso de la Práctica 0 jugó 44 100 partidas en menos de un minuto repartidas entre todos los núcleos, con controladores que se mueren pronto.

¿La mejora es real? Tres cuentas

Vuestra media no es «lo que vale» vuestro controlador: es lo que han dado esas partidas. Si repetís el mismo experimento con otras tantas, sale un número distinto. Estas son las tres cuentas que hay que hacer antes de quedarse con un cambio, con un ejemplo real de principio a fin.

1

Cuánto baila vuestra media

Aquí hay que separar dos cosas que se confunden todo el rato, porque son dos dispersiones distintas de dos cosas distintas.

La primera: las partidas no dan todas lo mismo. Con el mismo controlador y el mismo rival, una sale en 1 200 y la siguiente en 7 000. Lo que mide cuánto se separan unas partidas de otras es la desviación típica, y es una propiedad de vuestro controlador: jugar más partidas no la baja.

La segunda: lo que vais a comparar es una media de cien partidas, no una partida. Y las medias, como cualquier otra cosa que se mide, también se separan unas de otras: si lanzarais el experimento entero muchas veces, cada tanda de 100 partidas os daría una media distinta. Se separan mucho menos que las partidas sueltas —para eso se promedia—, pero se separan. Y a esa dispersión, la de las medias, es a la que se le llama error típico:

error típico  =  desviación típica de las medias  =  desviación típica de las partidas / √partidas

Conviene leer esa igualdad despacio, porque es la que contesta a la pregunta obvia: el error típico es una desviación típica. No es una media, ni se comporta «como si» fuera nada: es la desviación típica de otra cosa —de las medias en vez de las partidas—, y por eso se le aplican las mismas reglas que a cualquier desviación típica.

Falta justificar el segundo igual, que es de donde sale la raíz. Llamemos σ a la desviación típica de una partida, n al número de partidas y Var a la varianza, que es la desviación típica al cuadrado. La media de las n partidas es su suma dividida por n, y el camino es este:

#La cuentaPor qué vale
1 Var(Xi) = σ2 La varianza de cada partida. Es la misma para todas porque todas se juegan igual, con el mismo controlador y el mismo rival.
2 Var(X1 + … + Xn) = n · σ2 Las varianzas de cantidades independientes se suman, y aquí hay n sumandos iguales. Las partidas son independientes porque cada una arranca con su propia semilla.
3 Var(S / n) = Var(S) / n2 Al multiplicar una cantidad por una constante, su varianza queda multiplicada por el cuadrado de esa constante. Aquí la constante es 1/n.
4 Var(media) = n·σ2 / n2 = σ2 / n Meter el 2 dentro del 3. La varianza de la media se divide por n, no por n2, porque el numerador también llevaba una n.
5 error típico = √(σ2/n) = σ / √n Y la vuelta: la desviación típica es la raíz de la varianza.

O sea que la raíz no sale de ninguna parte especial: sale de que todo el camino hay que hacerlo en varianzas, porque es lo único que se puede sumar, y al final hay que volver. Y de ahí la consecuencia cara: como el error típico va con √n, partirlo por la mitad cuesta cuatro veces más partidas, y dividirlo por diez, cien veces más.

Si la cuenta no os dice nada, la intuición es esta: al promediar n partidas los errores de unas cancelan a los de otras. Si todos apuntaran en la misma dirección, promediar no serviría de nada; si se cancelaran del todo, quedaría cero. Como son al azar, el error de la suma no crece como n sino como √n —cien pasos en direcciones aleatorias te dejan a diez del origen, no a cien—, y al dividir la suma entre n queda σ/√n.

Y esto se vio en el concurso de la Práctica 0

Se jugó dos veces, primero con 10 partidas por emparejamiento y luego con 100. Si la fórmula es cierta, los errores típicos de la segunda tirada tienen que ser los de la primera divididos por √10 = 3,16. Los 21 controladores dan una razón media de 3,17.

Ejemplo. Medís vuestra versión actual con 100 partidas y Stats os da una media de 3 850 y una desviación típica de 2 100:

error típico = 2100 / √100 = 2100 / 10 = 210

Las partidas bailan ±2 100; vuestra media de cien baila ±210. O sea que ese 3 850 es en realidad «3 850, más o menos 210». No hace falta calcularlo a mano: es lo que devuelve getStandardError().

Lo que significa, en concreto: si repitierais el experimento muchas veces, dos de cada tres medias caerían a menos de un error típico de la verdadera, y sólo una de cada veinte se separaría más del doble.

Esos dos números no son de esta asignatura ni de este juego: salen de que las medias de muchas partidas se reparten, aproximadamente, como una campana de Gauss centrada en el valor verdadero, y en una campana el 68 % de los casos cae dentro de una desviación típica y el 95 % dentro de dos. Que se repartan así lo garantiza el teorema central del límite: la media de muchas medidas independientes tiende a la campana aunque las medidas de una en una no se parezcan a una campana ni de lejos. Y desde luego no se parecen: la puntuación de una partida suelta tiene suelo en 0, un pico donde se muere la mayoría y una cola larga hacia arriba cuando la píldora de poder sale bien.

Y ahí es donde encaja todo: la desviación típica de esa campana —la campana de las medias, no la de las partidas— es exactamente el error típico. Por eso la regla del 68 y el 95, que es una regla sobre desviaciones típicas, se lee directamente con él.

Y no hace falta creérselo: se comprueba

Si el error típico es la desviación típica de las medias, hay una forma directa de verlo: conseguid unas cuantas medias y calculadles la desviación típica. Lanzad veinte veces seguidas el mismo experimento de 100 partidas, meted las veinte medias en un Stats como si cada una fuera una observación, y pedidle su desviación típica: tiene que parecerse al error típico que os anunciaba cada tanda por separado. Ahí está la demostración de que la división por √n dice la verdad. 

Stats resumen = new Stats("las 20 medias");

for (int i = 0; i < 20; i++) {
    Stats[] tanda = executor.runExperiment(new MsPacMan(), ghosts, 100, "tanda " + i);
    System.out.printf("tanda %2d: media %8.1f, error típico anunciado %6.1f%n",
                      i, tanda[0].getAverage(), tanda[0].getStandardError());
    resumen.add(tanda[0].getAverage());   // una media, como si fuera una observación
}

// esta desviación típica ≈ el error típico de arriba: eso es lo que había que ver
System.out.println("Desviación típica de las 20 medias: " + resumen.getStandardDeviation());

De paso os contesta a la otra mitad: contad cuántas de las veinte medias caen a menos de un error típico de la media de todas. Salen unas catorce.

2

Si la diferencia cabe dentro del margen, no es una mejora

Ahora cambiáis una sola cosa —por ejemplo, la distancia a partir de la cual dais por peligroso a un fantasma, que pasa de 50 a 60 nodos—, volvéis a medir con otras 100 partidas y os sale 3 980. Habéis ganado 130 puntos. ¿Os lo quedáis?

La tentación es comparar los 130 puntos con el margen de una de las dos medidas. Pero el margen que hay que mirar es el de la diferencia, que tiene el suyo propio: las dos medias le meten cada una la suya.

Lo que no se hace es sumar los dos márgenes. Eso sería contar con que las dos medidas se equivocan a la vez y en sentidos contrarios, que es el caso peor y casi nunca ocurre: lo normal es que los dos errores se pisen un poco entre ellos. La regla correcta es que, cuando dos cantidades son independientes, lo que se suma no son sus desviaciones típicas sino sus varianzas, que son esas mismas desviaciones al cuadrado. Y aquí son independientes porque cada tanda juega partidas distintas: para esto sirve que no haya semilla fija. Que la diferencia sea una resta no cambia nada, porque restar dispersa tanto como sumar.

ETdiferencia2  =  ETvieja2 + ETnueva2   ⟹   ETdiferencia  =  2102 + 2102  =  √2 × 210  =  297

Mirad el número, que es la mitad de la explicación: sumando los dos márgenes saldría 420, y el de verdad es 297. Combinar dos errores independientes sale más barato que temerse lo peor. Y sí, la fórmula tiene la forma de la hipotenusa de un triángulo rectángulo y a mucha gente le sirve para acordarse, pero el motivo no tiene nada de geométrico: es, simplemente, que lo que se suma son los cuadrados.

Y ahora ya se puede aplicar la regla de la campana del paso anterior, porque vuelve a ser una desviación típica: si el cambio no sirviera absolutamente para nada, la diferencia entre las dos medias sería una campana centrada en 0 con esa dispersión. Y en una campana, 19 de cada 20 casos caen dentro de dos desviaciones típicas. O sea que una diferencia producida por puro azar se queda casi siempre por debajo de:

2 × error típico de la diferencia  =  2 × 297  =  594   ·   o sea, 2 × √2 ≈ 3 errores típicos

De ahí sale la regla de bolsillo, con el 3 en vez del 2,83 porque redondear hacia arriba aquí sólo os hace más prudentes:

creedla sólo si   |media nueva − media vieja|  >  3 × error típico

En el ejemplo, 3 × 210 = 630, y vosotros habéis sacado 130. No habéis mejorado nada, habéis cambiado de ruido: con esas dos medidas, la versión nueva y la vieja son indistinguibles. Y si algún día os sale justo por encima del umbral, repetid las dos medidas antes de celebrarlo.

Si las dos tandas no tienen el mismo número de partidas

El ×3 sale de suponer que las dos medidas se han hecho igual, con lo que sus dos errores típicos son parecidos y √(ET² + ET²) = √2 × ET. Si habéis medido una versión con 100 partidas y la otra con 400, usad la fórmula de la raíz con los dos errores típicos de verdad y comparad la diferencia con el doble de lo que salga.

3

Cuántas partidas harían falta para verlo

Si de verdad queréis saber si esos 130 puntos existen, hay que jugar más partidas. Cuántas sale de juntar las dos fórmulas anteriores: queréis que la diferencia supere 3 errores típicos, y el error típico es sd / √partidas, así que basta con despejar de diferencia > 3 sd / √partidas:

partidas  ≈  ( 3 × desviación típica / diferencia )2

Con la desviación típica de 2 100 y los 130 puntos del ejemplo: (3 × 2100 / 130)2 = 48,52 ≈ 2 350 partidas por versión, o sea casi cinco mil en total, sólo para confirmar una mejora del 3 %. Cuánto tiempo de máquina son esas 5 000 partidas os lo dice getMsTaken(), y cambia mucho de un controlador a otro.

Conviene tener esta tabla a mano antes de ponerse a medir: dice, para cada número de partidas, cuál es la mejora más pequeña que podríais llegar a ver. Está calculada con una desviación típica de 2 000 puntos, que es un orden de magnitud razonable; la vuestra os la dice getStandardDeviation():

La conclusión práctica

Medir barato sólo detecta mejoras grandes. Con 100 partidas, que es lo que vais a lanzar mientras trabajáis, cualquier cosa por debajo de 600 puntos es invisible. Así que id a por los cambios que mueven la media cientos de puntos —comer la píldora de poder cuando toca, dejar de meterse en tramos cerrados— y no gastéis la tarde moviendo una constante de 50 a 52 a ver si sube: para demostrar una mejora de 50 puntos harían falta más de 14 000 partidas por versión.

No hay semilla fija

El Executor crea su Random sin semilla, así que dos ejecuciones del mismo experimento no dan el mismo número y dos controladores distintos no juegan las mismas partidas. No es un fallo: es lo que obliga a mirar medias de muchas partidas en vez de casos. Si al comparar dos versiones os sale una diferencia pequeña, volved a lanzar las dos antes de creérosla.

03

El concurso: todos contra todos

Cada práctica con competición se cierra igual: se cogen los controladores tal y como se entregaron, se enfrenta cada Ms. Pac-Man a cada conjunto de fantasmas, y de esa tabla salen los dos rankings. Con trece grupos son 169 emparejamientos y, a 300 partidas cada uno, 50 700 partidas.

Las medias de la derecha son el ranking de Ms. Pac-Man: cuánto puntúa cada una contra todos los fantasmas del curso. Las de abajo son el de los fantasmas: cuánto dejan puntuar a todas las Ms. Pac-Man del curso. Son los datos reales del curso pasado.

Lanzarlo vosotros

El motor ya trae el evaluador, así que podéis jugar vuestro propio concurso en casa con todos los controladores que tengáis a mano. Son dos archivos. El primero, un main de tres líneas: 

import es.ucm.fdi.ici.PacManParallelEvaluator;
import es.ucm.fdi.ici.Scores;

public class Evaluate {
    public static void main(String[] args) {
        PacManParallelEvaluator evaluator = new PacManParallelEvaluator();
        Scores scores = evaluator.evaluate();
        scores.printScoreAndRanking();     // la tabla y los dos rankings
    }
}

El segundo es config.properties, y dónde lo pongáis importa: va en la raíz de src, al lado de la carpeta es de vuestros paquetes, y no en la carpeta del proyecto.

El motivo es que el evaluador no abre un fichero por su ruta: le pide a Java un recurso llamado config.properties, y Java los busca donde estén las clases ya compiladas, que en Eclipse es la carpeta bin. Lo que hace que esto funcione es que Eclipse copia a bin todo lo que encuentra en src y no sea código Java, así que un archivo puesto aquí acaba también allí:

Cuatro cosas que descalifican sin que os enteréis

1 · getName() tiene que ser único

El evaluador guarda los resultados en una tabla indexada por el nombre que devuelve getName(), no por la clase. Dos controladores con el mismo nombre son la misma fila: los resultados de uno pisan los del otro y el segundo se queda con la media a cero. Y si no lo sobreescribís, Controller devuelve "Unknown Controller" para todos, con lo que todos los grupos que lo olviden colisionan entre sí. El curso pasado pasó, y más de una vez.

Poned algo inconfundible y con la letra del grupo dentro, en los dos controladores.

2 · Una excepción no resta: repite la partida

Cuando vuestro controlador lanza una excepción, runExperiment la captura, imprime la traza, descarta esa partida y la vuelve a jugar con otra semilla hasta completar las 300. O sea que un fallo ocasional no baja la media —sólo cuentan las partidas que terminan—, pero un fallo sistemático deja al evaluador dando vueltas para siempre en esa casilla y cuelga el concurso entero.

Antes de entregar: 300 partidas seguidas contra varios rivales, con la consola a la vista y sin una sola traza. Si aparece una, es un camino[1] sin comprobar la longitud, o un fantasma en la cárcel al que le habéis pedido la distancia.

3 · No se juega contra el rival, se juega contra el juego

Antes de cada partida el motor llama a preCompute(String opponent) y os pasa el nombre de la clase del rival. Está ahí por la Práctica 6, donde hace falta cargar la base de casos. Usarlo para cambiar de comportamiento según quién esté enfrente —y muy en particular para que vuestros fantasmas se dejen comer por vuestra Ms. Pac-Man— es hacer trampa, se ve leyendo el código y deja los dos controladores fuera del concurso.

4 · Nada que dependa del entorno

El evaluador corre varios emparejamientos a la vez, en hilos distintos y con instancias distintas de vuestra clase. Un static mutable se comparte entre partidas simultáneas y os va a dar resultados imposibles de reproducir. Y nada de leer o escribir ficheros, abrir ventanas, lanzar hilos propios o llamar a System.exit: además de estar prohibido por el enunciado, tumba la ejecución de todos los demás.

04

Cómo se calcula el ranking

Hay dos rankings independientes, uno de Ms. Pac-Man y otro de fantasmas, y cada controlador entra sólo en el suyo. Un grupo puede ganar uno y quedar último en el otro; de hecho es lo normal.

1

La media de cada casilla

Cada emparejamiento se juega 300 veces y se guarda la media de la puntuación final de esas 300 partidas. Ni la mejor, ni la mediana: la media, que es lo que devuelve Stats.getAverage().

2

La media de cada controlador

La puntuación de una Ms. Pac-Man es la media de su fila: lo que saca, de media, contra los fantasmas de todo el curso. La de unos fantasmas es la media de su columna: lo que dejan sacar, de media, a las Ms. Pac-Man de todo el curso. Como todas las casillas tienen las mismas 300 partidas, es exactamente la media de las 3 900 partidas de ese controlador.

3

El orden

En Ms. Pac-Man gana la media más alta. En fantasmas gana la más baja: vuestro trabajo es que la gente no puntúe. Es literalmente el mismo número leído al revés, y por eso no hace falta inventarse una métrica de «cuánto dañan»: la puntuación del rival ya lo es.

Por qué la media de la fila y no otra cosa

Porque todos juegan contra exactamente el mismo campo. Si a alguien le tocan fantasmas duros, le tocan a todos; si un grupo entrega unos fantasmas que no persiguen, ese regalo se lo reparten las trece Ms. Pac-Man por igual. Con la matriz completa, la media de la fila es una comparación limpia y no hace falta corregir nada.

05

El punto extra

La competición reparte un punto sobre la nota de la práctica, y se reparte en dos mitades independientes: medio punto por el ranking de Ms. Pac-Man y medio punto por el de fantasmas. En cada uno, el mejor se lleva su medio punto entero y el peor se queda a cero; los de en medio, lo que les toque en proporción.

Ms. Pac-Man · más es mejor 0,5 × (mía − peor) / (mejor − peor)
Fantasmas · menos es mejor 0,5 × (peor − mía) / (peor − mejor)

Donde mía es la media de vuestra fila o vuestra columna, y mejor y peor son la mayor y la menor de ese ranking. Para los fantasmas, mejor es la media más baja. El resultado se redondea a dos decimales y los dos medios puntos se suman.

Con los números del curso pasado

Aplicando esta regla a los resultados reales de la Práctica 1 del año pasado, el reparto habría quedado así:

Mide la distancia al mejor, no el puesto

Comparad las dos tablas. Los segundos fantasmas se llevan el medio punto entero porque quedaron a quince puntos del primero: en la práctica empataron. La segunda Ms. Pac-Man se lleva 0,19 porque la primera le sacó casi el doble. No es una nota por posición en la lista, es una nota por lo cerca que quedasteis del mejor, y eso es deliberado: quedar segundo a un palmo vale casi tanto como ganar, y quedar segundo a media tabla de distancia, no.

La letra pequeña

CasoQué pasa
Un controlador no compila, o no juega Queda fuera del concurso y se lleva 0 en su ranking. Y no entra en la escala: no sirve de suelo para subir a los demás.
Un controlador falla en algunas partidas Esas partidas se repiten, así que sólo cuentan las que terminan. Si falla siempre, es el caso anterior.
Dos medias iguales Mismo punto para los dos. No hay desempate.
Sólo hay dos participantes, o todos empatan Si mejor y peor coinciden, todo el mundo se lleva el medio punto.
El punto extra y la nota Se suma a la nota de la práctica, que se corrige aparte por código y por rendimiento. El punto no sustituye a nada: es extra.
Es una nota relativa, con lo que eso implica

Los dos extremos los ponéis vosotros, no yo: la escala se construye con los controladores que se entreguen ese año. Un grupo que se salga de la tabla comprime a todos los demás hacia abajo, y un controlador muy flojo estira la escala por el otro lado. Es lo que tiene un concurso, y es también la razón de que el grueso de la nota de la práctica no dependa de esto.

06

Guardar métricas y logs

A la cuarta variante ya no vais a saber si el 2 750 era la de antes o la de ahora, así que conviene apuntarlas desde la primera. El motor trae lo justo para no montar nada: Stats sabe convertirse en una línea de texto y volver de ella. 

// Una línea por cada variante que probéis, en un CSV que se abre con cualquier hoja de cálculo
try (PrintWriter out = new PrintWriter(new FileWriter("medidas.csv", true))) {

    for (GhostController rival : rivales) {
        Stats[] s = executor.runExperiment(new MsPacMan(), rival, 100,
                                           "v7-umbral60 vs " + rival.getName());

        out.println(s[0].fileRepresentation(";"));   // ms;descripción;max;min;n;sumsq;suma
        System.out.printf("%-28s media %8.1f ± %5.1f  (peor %5.0f)%n",
                          rival.getName(),
                          s[0].getAverage(),
                          s[0].getStandardError(),
                          s[0].getMin());
    }
}

La descripción que se le pasa a runExperiment acaba dentro del CSV, así que metedle la versión del controlador y los umbrales que estáis probando: dentro de dos semanas es lo único que os va a permitir saber qué era cada fila.

Una traza por turno, sin llenar la consola

El Executor tiene un gancho para esto que casi nadie usa: setPeek recibe una función que se llama en cada turno con el Game. Sirve para sacar una serie temporal de lo que os interese sin ensuciar el controlador: 

Executor executor = new Executor.Builder()
        .setTickLimit(4000)
        .setPeek(game -> String.format("%d;%d;%d;%d",
                 game.getTotalTime(),
                 game.getScore(),
                 game.getNumberOfActivePills(),
                 game.getPacmanNumberOfLivesRemaining()))
        .build();

¿Y dónde acaba lo que devuelve esa función? En el log del motor, que no es ningún fichero: el simulador usa SLF4J con la implementación slf4j-simple, y ésa, mientras no se le diga otra cosa, escribe en la salida de error. O sea que sale por la consola de Eclipse, en rojo, con este aspecto: 

[main] INFO pacman.Executor - 1247;3120;41;2

Con 4 000 líneas por partida, en la consola no sirve de nada. Para llevarlo a un fichero hay que decírselo a esa implementación con una propiedad de la máquina virtual, en Run Configurations… > Arguments > VM arguments: 

-Dorg.slf4j.simpleLogger.logFile=medidas.log

A partir de ahí, medidas.log aparece en la carpeta del proyecto y se abre como cualquier CSV. Dos avisos: el fichero se sobrescribe en cada ejecución, y esto es para un experimento vuestro, no para el concurso —el evaluador se construye su propio Executor y ahí no hay dónde enganchar un peek—.

El System.out.println dentro de getMove

Es el reflejo natural y es un problema serio aquí: se llama 4000 veces por partida. En un experimento de 300 son más de un millón de líneas, la consola de Eclipse se atraganta y el experimento pasa de tardar dos minutos a tardar veinte. Si necesitáis imprimir, que sea detrás del mismo interruptor que la depuración visual, o sólo en los cruces.

07

Depurar y ver lo que está pasando

Los errores de un controlador casi nunca se ven leyendo el código: se ven en pantalla, en dos partidas. Estas son las cuatro herramientas, de menos a más.

1 · La partida a cámara lenta

runGame(pacMan, ghosts, delay) con setVisual(true). El delay son los milisegundos de pausa entre turnos: con 5 va rapidísimo y no se ve nada, con 40 va al ritmo del juego, y con 150 se pueden seguir las decisiones de una en una. Es lo primero que hay que hacer cuando algo va mal, siempre.

2 · Pintar lo que el controlador está pensando

GameView dibuja encima del laberinto: un color por motivo, y todo detrás de un interruptor que se apaga al entregar. Lo del interruptor no es una manía de estilo, por el motivo que viene justo debajo. 

if (Constantes.DEBUG_PACMAN) {
    GameView.addPoints(game, Color.ORANGE, caminoElegido);      // a dónde voy
    GameView.addPoints(game, Color.RED,    tramosDescartados);  // qué he descartado, y por qué
    GameView.addLines (game, Color.CYAN,   miNodo, nodoDelFantasmaQueMePreocupa);
}

Lo importante no es pintar el camino bueno: es pintar lo que has descartado. Un controlador que se queda encerrado sin motivo aparente os lo explica solo en cuanto veis de rojo los tres tramos que ha dado por cerrados.

Dejarlo encendido tumba la corrección, y no es una exageración

GameView.addPoints y addLines no dibujan: apuntan lo que hay que dibujar en dos listas static, y el motor las vacía al repintar la ventana. En un experimento sin ventana no repinta nunca, así que las listas crecen turno a turno y no las vacía nadie. Y no vale con que no haya ventana: el interruptor del propio motor, GameView.isVisible, nace a true y no lo pone a false nadie —podéis buscarlo—.

En una partida suelta da igual. En las decenas de miles de partidas de un concurso, se acaba la memoria y se cae la ejecución entera, la vuestra y la de todos los demás. Pasó con las entregas de la Práctica 0 la primera vez que se lanzó el concurso con 100 partidas por emparejamiento. Por eso «apagad la depuración» está en la lista de comprobación de la entrega, y por eso el interruptor tiene que envolver la llamada, no ir por dentro.

3 · Grabar la partida rara y volver a verla

La partida en la que pasó la cosa imposible no se repite: cada una tiene una semilla nueva. Por eso el motor sabe grabarlas y reproducirlas: 

executor.runGameTimedRecorded(pacMan, ghosts, "partida-rara.txt");
// y luego, las veces que haga falta:
executor.replayGame("partida-rara.txt", true);

La repetición guarda el estado del juego turno a turno, no vuestras decisiones, así que sirve para ver qué pasó, no para depurar con puntos de ruptura. Para eso está lo siguiente.

4 · Un aviso en cada decisión

runGame admite un GameObserver, al que el motor avisa de cada movimiento indicando además si se tomó en un cruce. Es la forma limpia de contar cosas —cuántas decisiones reales tomáis, cuántas veces devolvéis null— sin meter contadores dentro del controlador: 

executor.runGame(pacMan, ghosts, 40, new GameObserver() {
    public void pacManMove(MOVE move, boolean inJunction) {
        if (inJunction) decisiones++;
    }
    public void ghostsMove(EnumMap<GHOST, MOVE> moves, EnumMap<GHOST, Boolean> inJunction) { }
});

08

Contra quién probar

Medir contra un solo rival no vale: se acaba afinando el controlador contra ese rival, que es justo lo que el concurso castiga. Por orden de facilidad:

RivalPara qué sirve
Los vuestros, entre ellos El mejor banco de pruebas que vais a tener: los dos conocen las mismas debilidades, y cada arreglo de un lado destapa un agujero del otro.
Los de la Práctica 0 Aleatorios, agresivos y huidizos. Son la línea base: si no ganáis holgadamente a GhostsRandom, no hay nada que afinar todavía.
Los de otros grupos Intercambiad los .class ya compilados, nunca el código fuente. Es lo más parecido al concurso que podéis montar, no hay nada que copiar en un compilado, y se aprende mucho más perdiendo contra alguien que ganando a un aleatorio.
Los de cursos anteriores Se publican en el Campus Virtual a principios de la segunda semana de la Práctica 1, la del 28 de septiembre. Vienen en un .jar que se añade al proyecto con Build Path > Add JARs y se referencia en config.properties por su nombre de clase completo, igual que los vuestros. Son controladores que ya compitieron en su año, así que os dicen en qué parte de la tabla estáis de verdad, y no sólo en qué parte de la vuestra.
Y el calendario de todo esto

Medir cuesta tiempo de reloj, y sobre todo cuesta repetir: cada vez que cambiáis algo hay que volver a lanzar las dos versiones, y ninguna medida vale hasta que termina. Eso significa que la víspera de la entrega no da tiempo a hacer esto bien. Reservad la última tarde para limpiar y comprobar la lista de la entrega, no para descubrir que el controlador falla una partida de cada treinta.

09

Los dos archivos, para llevar

Todo lo de esta guía se monta con dos archivos, y son los mismos con los que se jugó el concurso de la Práctica 0. Los dos van en la raíz de src, uno al lado del otro, en un proyecto que dependa de MsPacManEngine:

  • Concurso.java→ El main del concurso · 263 líneas Lanza el evaluador, agrega las medias de cada fila y de cada columna, imprime los dos rankings con su error típico y el reparto del punto extra, y deja la tabla completa en un CSV. Trae comentado por qué hace cada cuenta, y el hilo que vacía lo que los controladores pintan con GameView, sin el cual un concurso largo se queda sin memoria.
  • config.properties→ Quién juega y cuántas partidas Viene con los 42 controladores de la Práctica 0 y trials = 100. Cambiad las dos listas por vuestras clases y ya está. Acordaos de que se carga del classpath: tiene que quedar en src para que Eclipse lo copie a bin.
Lo mínimo para que arranque

Proyecto nuevo con MsPacManEngine en el Build Path, los dos archivos en src, vuestras clases en las dos listas de config.properties, y Run As > Java Application sobre Concurso.java. El CSV aparece en la carpeta del proyecto —hay que refrescar con F5 para verlo desde Eclipse—.
