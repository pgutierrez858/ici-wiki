Asignatura / Guías / Depurar reglas borrosas

Depurar reglas borrosas Qué entra, cuánto se activa cada regla, y qué sale.

Con Jess, en cada turno se disparaban unas reglas y otras no. Aquí casi todas se activan un poco, se mezclan, y lo que sale es un número por acción. Eso es lo bueno de la lógica borrosa y también lo que la hace difícil de seguir. Esta guía da dos herramientas para verlo, una para probar el FCL sin jugar y otra para seguirlo mientras se juega, con el código entero y lo que sacan de verdad con el ejemplo de las siete reglas.

01

Tres preguntas, en este orden

Cuando Ms. Pac-Man hace algo raro, la causa está en uno de tres sitios. Id en orden: no tiene sentido revisar una acción si su salida nunca es la más alta.

PreguntaSi la respuesta es noCómo se mira
1 · ¿Las entradas valen lo que creéis? Un fallo de Java: una distancia mal calculada, un -1 que se cuela, una variable que no se rellena. La traza: escribe las entradas de cada turno.
2 · ¿Gana la salida que esperáis? Los términos no están donde creéis, una regla no se activa, o se activa otra con más fuerza. O un empate. Un caso en ProbarBorroso, con su curva de control. El resumen de la traza dice qué reglas no se activan nunca.
3 · ¿La acción hace lo que debe? El problema ya no es borroso: es Java, como en la Práctica 1. VerPartida despacio, con la traza diciendo qué acción se está ejecutando.

Todo el código de esta página está en el proyecto del ejemplo, en el paquete depurar.

02

Probar el FCL sin jugar

Una partida dura miles de turnos y la situación que os interesa sale una vez, o ninguna. Es mucho más rápido escribir esa situación a mano, como tres números, y preguntarle al FCL qué haría. Eso hace ProbarBorroso: carga el .fcl directamente con jFuzzyLogic, sin juego, y para cada caso dice qué salida gana y si es la que esperabais. 

static final String FCL = "bin/es/ucm/fdi/ici/c2627/practica4/grupoYY/mspacman-v1.fcl";
static final String BLOQUE = "MsPacMan";

public static void main(String[] args) {
    FIS fis = FIS.load(FCL, true);         // true: si hay un error de sintaxis, lo dice
    if (fis == null) { System.out.println("No encuentro " + FCL); return; }
    FunctionBlock fb = fis.getFunctionBlock(BLOQUE);

    //   nombre del caso                         gana esperada   peligro comestible ppill
    caso(fb, "nada cerca: come",                     "comer",     150, 150, 150);
    caso(fb, "peligroso a 10: huye",                 "huir",       10, 150, 150);
    caso(fb, "peligroso a 45: todavía come",         "comer",      45, 150, 150);
    caso(fb, "comestible a 10, peligroso lejos",     "perseguir", 150,  10, 150);
    caso(fb, "comestible a 10, peligroso a 10",      "huir",       10,  10, 150);
    caso(fb, "peligroso a 20 y ppill a 5: a la ppill", "irAPPill", 20, 150,   5);
    …
}

static void evaluar(FunctionBlock fb, double peligro, double comestible, double ppill) {
    fb.setVariable("peligro", peligro);   // a todas las entradas, cada vez: si no, se quedan con el valor anterior
    fb.setVariable("comestible", comestible);
    fb.setVariable("ppill", ppill);
    fb.evaluate();
}

Todos los casos bien.

Cada caso dice tres cosas: si gana la esperada, cuánto vale cada salida, y con qué grado se ha activado cada regla (sólo las que pasan de 0). Cuando un caso sale MAL, las dos últimas líneas suelen bastar para ver por qué.

La curva de control

Un caso prueba un punto. La curva prueba todos: mueve una entrada de punta a punta, con las otras quietas, y escribe lo que sale en cada sitio. ProbarBorroso la saca después de los casos, para peligro de 0 a 100 con todo lo demás lejos: 

peligro  salidas → gana
   20   comer=1.4 huir=8.6 irAPPill=0.0 perseguir=0.0 → huir
   25   comer=3.0 huir=8.4 irAPPill=0.0 perseguir=0.0 → huir
   30   comer=4.1 huir=8.2 irAPPill=0.0 perseguir=0.0 → huir
   35   comer=5.0 huir=0.0 irAPPill=0.0 perseguir=0.0 → comer
   …
   65   comer=6.8 huir=1.6 irAPPill=0.0 perseguir=0.0 → comer

En la curva se ven cosas que con casos sueltos se escapan: el punto exacto en que cambia la acción (entre 30 y 35), un salto brusco (huir de 8,2 a 0: ninguna regla de huir para media), o un tramo en el que dos salidas valen lo mismo. Para una curva de otra entrada, cambiad la variable que se mueve en el bucle del main.

Un caso por regla, desde el principio

Cada regla nueva, con la situación para la que la escribís y la acción que debería ganar. Si una regla posterior la rompe, os enteráis en un segundo. En el ejemplo, el caso "peligroso a 45: todavía come" fue el que destapó un empate a 5,0 en la primera versión del paso 2.

03

Ver las reglas mientras se juega

El motor trae un observador, ConsoleFuzzyEngineObserver, que escribe en cada turno todas las entradas, todas las salidas y todas las reglas. Son unas veinte líneas por turno, y una partida tiene miles. TrazaBorrosa hace lo mismo en una línea, sólo cuando cambia la acción ganadora, y al final un resumen: 

public class TrazaBorrosa implements FuzzyEngineObserver {

    public TrazaBorrosa(String nombre, FuzzyEngine motor, boolean soloCambios) { … }

    /** El FuzzyEngine avisa después de cada turno, con lo que ha entrado y lo que ha salido. */
    @Override
    public void actionFired(String accion, HashMap<String, Double> entradas,
            HashMap<String, Double> salidas, Collection<String> nada) {
        turno++;
        StringBuilder activas = new StringBuilder();
        for (Rule r : reglas) {                           // las del FIS del motor
            double grado = r.getDegreeOfSupport();
            if (grado <= 0) continue;
            turnosRegla.merge(r.getName(), 1, Integer::sum);
            activas.append(String.format(" R%s:%.2f", r.getName(), grado));
        }
        vecesGana.merge(accion, 1, Integer::sum);
        if (!soloCambios || !accion.equals(ganadora))
            System.out.printf("[%s] t=%d  %s → %s → gana %s.  Reglas:%s%n", …);
        ganadora = accion;
    }

    /** Llamadlo al final: una regla que no se activa nunca no hace nada. */
    public void resumen() { … }
}

El FuzzyEngine no deja ver su FIS, así que TrazaBorrosa lo coge por reflexión al crearse y lee el grado de cada regla directamente. Lo mismo hacía TrazaReglas con el Rete de Jess.

Engancharla

MsPacMan pacman = new MsPacMan();
TrazaBorrosa traza = new TrazaBorrosa("MSPACMAN", pacman.getMotor(), true);   // true: sólo los cambios

executor.runGame(pacman, new GhostsAggressive(), 40);
traza.resumen();

Es lo que hace VerPartida. Con false escribe una línea en cada turno, que viene bien para seguir unos pocos turnos con el juego a 200 ms. Para los fantasmas, una traza por fantasma con getMotor(GHOST.BLINKY), etc.

  • Las entradas, entre llaves. Lo primero que hay que mirar: si una distancia vale algo raro, el problema es de Java y el FCL no tiene la culpa.
  • Las salidas, y la que gana. Fijaos en lo cerca que están a veces: en el turno 61, irAPPill le gana a comer por tres décimas.
  • Las reglas activas, con su grado. En el turno 79, la regla 1 se activa sólo con 0,10, y basta para que gane huir: como su salida no tiene ninguna otra regla activa, su centro de gravedad es 8,1 aunque el grado sea pequeño. Es la trampa del término solo, y se ve aquí mejor que en ningún sitio.

El turno 61 es el que explica por qué la v1 no mejora: con el fantasma a 69 pasos, NOT lejos vale 0,44 y la regla 7 manda a Ms. Pac-Man a gastar la píldora de poder. Está contado en el paso 4 de la guía.

04

El resumen: las reglas que no existen

Al final de esa misma partida:

[MSPACMAN] 4001 turnos. Turnos en que se activa cada regla:
     3352  RULE 1
      492  RULE 2
     3352  RULE 3
      384  RULE 4
      492  RULE 5
      220  RULE 6
      117  RULE 7
[MSPACMAN] Veces que gana cada acción:
      415  comer
     3268  huir
      110  irAPPill
      208  perseguir

Una regla que en una partida entera se queda a 0 sale marcada con <-- NUNCA, y no hace nada, por bien escrita que esté. Las causas típicas: un término que no llega a las distancias que salen en el juego, un AND de dos cosas que nunca pasan a la vez, o un nombre de término mal escrito en otra regla que la tapa.

La otra mitad del resumen también dice mucho. Contra los agresivos, esta Ms. Pac-Man huye en 3 268 de 4 001 turnos: casi todo el tiempo. Si queréis que puntúe más, ahí está el margen, y no en afinar la regla 7, que gana 110 veces.

Activarse no es ganar

Con Jess, una regla que se disparaba ponía su ACTION en la memoria, ganara o no. Aquí una regla activa con 0,04 contribuye casi nada. Mirad las dos columnas a la vez: una regla que se activa en miles de turnos pero cuya acción no gana nunca, o casi nunca, seguramente tiene la salida mal puesta, o hay otra regla que siempre la supera.

05

Empates y huecos

En Jess, si ninguna regla asertaba un ACTION, el motor devolvía NEUTRAL y se veía. Aquí siempre gana alguien, aunque sea por accidente, y eso esconde dos problemas:

Lo que pasaCómo se veQué hacer
Un hueco: para unas entradas, ninguna regla de una salida se activa. Esa salida vale su DEFAULT. Si todas lo hacen, todas valen 0 y gana la primera del array. Mirad la curva de control: un salto a 0 es un hueco. Términos que se solapen, o reglas que cubran ese tramo.
Un empate: dos salidas con el mismo término activo y nada más. Valen lo mismo, 5,0 y 5,0, o 8,7 y 8,7. Gana la que vaya antes en el array de acciones. Que la regla que debe ganar baje la otra salida: THEN perseguir IS mucho, comer IS poco.

Los dos son fáciles de pillar con ProbarBorroso, porque las salidas aparecen con su valor: un caso que gana "por los pelos" con dos salidas iguales es un empate, aunque salga BIEN.

06

Sin escribir Java

Para probar una idea rápida hay dos atajos. El primero, el banco de los apuntes, en Inferencia borrosa, o el de la guía del ejemplo, que ya tiene cargado el FCL de las siete reglas: pegáis vuestro FCL, movéis las entradas y veis los recortes, las salidas y la curva. Da las mismas cifras que jFuzzyLogic.

El segundo, la consola de jFuzzyLogic, que viene en MsPacManEngine/lib: 

java -jar jFuzzyLogic.jar -e mspacman-v1.fcl 150 20 10
	VAR_OUTPUT	     comer = 1.397199
	VAR_INPUT 	comestible = 150.000000
	VAR_OUTPUT	      huir = 4.838223
	VAR_OUTPUT	  irAPPill = 8.663333
	VAR_INPUT 	   peligro = 20.000000
	VAR_OUTPUT	 perseguir = 0.000000
	VAR_INPUT 	     ppill = 10.000000
	RULE_BLOCK reglas
		Support  	Rule name 	Rule
		0.750000	1         	IF peligro IS cerca THEN huir IS mucho;
		…
		1.000000	7         	IF (peligro  IS NOT lejos) AND (ppill IS cerca) THEN irAPPill IS mucho , huir IS poco;

Dos avisos. Los números se asignan a las entradas en orden alfabético, no en el de VAR_INPUT: aquí comestible, peligro, ppill. Mirad siempre las líneas VAR_INPUT. Y después de escribir los valores abre una ventana con las gráficas de cada variable; el programa no termina hasta que la cerráis.

07

Errores típicos de la práctica

Lo que pasaPor qué, y qué hacer
Al arrancar sale Can't load file, y luego Error evaluating fuzzy logic en cada turno. Ms. Pac-Man no se mueve.La ruta del .fcl no existe desde la carpeta en la que se lanza el programa: FCL_PATH sin vuestra letra, o el fichero sin copiar a bin/. Project > Clean, y probad la ruta con ProbarBorroso.
No such variable: 'Peligro', en cada turno.Una clave del mapa del Input no coincide con un nombre de VAR_INPUT. Las mayúsculas cuentan. También pasa si una versión vieja del .fcl no declara una entrada que añadisteis después.
El fichero carga, pero en cada turno sale Error evaluating fuzzy logic con un NullPointerException.El tercer argumento del FuzzyEngine es el nombre del FUNCTION_BLOCK, no el del fichero, y no coincide.
Una acción no gana nunca, aunque sus reglas se activan.Su VAR_OUTPUT no se llama como su getActionId(), o su salida está en otra escala. Las mayúsculas cuentan también aquí.
Con dos salidas iguales gana siempre la misma, o una distinta en cada ejecución.Un empate. Con el MaxActionSelector del ejemplo gana la primera del array; con uno que recorra el HashMap de salidas, cualquiera. Ved la sección 5.
Un fantasma que no existe hace huir a Ms. Pac-Man.Un -1 como distancia, fuera de los términos: vale "cerca" con un 1. "No hay" tiene que ser un número dentro del rango, como LEJOS.
Las entradas valen siempre lo mismo, o lo del turno anterior.Atributos del Input inicializados en la declaración, que pisan lo que calcula parseInput; o una variable que no se manda en algún turno. Ved las entradas.
Una regla con NOT se activa mucho más de lo que esperabais.NOT lejos no es cerca: es 1−μ1 - \mu1−μ, y vale algo en todo el tramo en que lejos no es 1. El paso 4 del ejemplo.
Una regla con OR y AND se activa cuando no debería.jFuzzyLogic lee de izquierda a derecha, sin precedencia. Paréntesis.
Con METHOD : MM salen valores absurdos, cerca de 0.Un error de jFuzzyLogic 3.2 con la media de los máximos. Usad COG.
TrazaBorrosa o un ConsoleFuzzyEngineObserver enganchados en la entrega.Escriben en cada turno y ralentizan el concurso. Fuera antes de subir el zip.
